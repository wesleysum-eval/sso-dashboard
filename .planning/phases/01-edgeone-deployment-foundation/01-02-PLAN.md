  <action>
    Create `edge-functions/api/kv-check.js` under `edge-functions/` (never
    `cloud-functions/` — KV is Edge-Functions-only per RESEARCH.md's Architectural
    Responsibility Map and Pitfall 1) exporting a single `onRequest({ request })` handler
    per RESEARCH.md Pattern 3:

    - On `POST`: parse the JSON body, take `value` (coerce to `String`; if absent, fall
      back to `String(Date.now())`), and call `my_kv.put('phase1_check', value)`. The KV
      key is the hardcoded literal `phase1_check` — never derived from client input, so
      the platform's key-charset restriction (letters/digits/underscore only, no `:`) is
      structurally satisfied without extra validation logic. Return
      `{ wrote: true, value }` as JSON.
    - On `GET` (any other method): call `my_kv.get('phase1_check')` and return
      `{ value }` as JSON, where `value` is `null` if nothing has been written yet.
    - Guard both branches with `typeof my_kv !== 'undefined'` and return a `503` with
      `{ error: 'kv not bound' }` if the global is missing — this makes a still-unbound
      namespace fail loudly (clear signal) instead of the silent `undefined` no-op
      RESEARCH.md's Pitfall 1 warns about.

    Deploy: `edgeone makers deploy`. Re-capture the live URL from CLI stdout and
    overwrite `.planning/phases/01-edgeone-deployment-foundation/DEPLOYED-URL.txt` (the
    production domain is expected to stay stable across redeploys of the same project,
    but re-capturing rather than assuming keeps this plan's own rule — never hardcode an
    assumed domain — self-consistent).

    Issue the write and the read close together in the same verification pass, since KV
    is eventually consistent across edge nodes (up to ~60s) but immediately consistent
    for the node that performed the write — per RESEARCH.md's Pitfall 2, don't treat a
    slow cross-node read as a deploy bug.
  </action>
