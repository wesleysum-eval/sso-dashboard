# Phase 4.1 Plan 2: Dashboard Renderer & Insights Polish — Save/Preview UI Summary

**Copy Link clipboard affordance plus a four-state dashboard-state badge (Generating…/Draft/Saved/Saved·Read-only), both driven entirely by already-in-memory fetch responses — zero new backend routes.**

## Accomplishments

- Added `.dashboard-state-badge` (+ `.is-saved` accent modifier) CSS to `index.html`, built exclusively from existing `:root` tokens, borrowing `.tenant-badge`'s pill shape only (never its hardcoded hex colors); wrapped `.prompt-panel h2` and the new `<span id="dashboard-state-badge">` in a flex row, hidden by default.
- Added `setDashboardStateBadge(text, isSaved)` — a presentation-only helper in `app.js` — and wired it into all four lifecycle states: the `generateBtn` click handler (`'Generating…'`), the generation success branch (`'● Draft — not saved'`), `saveDashboard()`'s success branch (`'✓ Saved'`, driven off the same already-in-memory `POST /api/dashboard` response), and `renderRetrievalView()`'s success branch (`'✓ Saved · Read-only'`, unconditional). A failed generation leaves whatever badge state was showing unchanged.
- Added `.copy-link-btn` CSS (adds only `margin-left: 8px`; chrome comes from the existing `.btn-secondary` class) and a "Copy Link" `<button>` appended right after the bookmarkable `<a>` link inside `saveDashboard()`'s success branch. Reuses the same `url` variable already constructed for the link — never rebuilds it. Calls `navigator.clipboard.writeText(url.toString())`, toggling the button to "Copied!" for 2 seconds on success; silently stays "Copy Link" on rejection/unavailability (guarded with an early return if the Clipboard API doesn't exist).

- Copy Link's click handler reuses the exact same `url` object already built for the adjacent bookmarkable link — never re-derives or duplicates the URL construction.
- Split what the plan wrote as two tasks touching the same `saveDashboard()` success branch into two genuinely separate atomic commits, by temporarily removing Task 2's code before committing Task 1, then re-adding and committing Task 2 — preserves the plan's task-level commit granularity despite the code proximity.
