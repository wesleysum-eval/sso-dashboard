## Summary

Reviewed the four files this phase touched: `generation-schema.js`, `generate.js`, `app.js`, and `index.html`. Two positive confirmations first, since these were the review's explicit focus areas:

- **GEN-03's constrained-generation vocabulary is untouched.** `COMPONENT_TYPES`, `METRICS_BY_SOURCE`, `INTERVALS`, `TIME_RANGES`, and `validateWidget()` are byte-identical to Phase 4 (`git diff 3bcc7b4 HEAD -- edge-functions/lib/generation-schema.js` shows only additive `METRIC_LABELS`/`validateDashboardTitle` hunks). No new componentType, no LLM-writable enum expansion.
- **No XSS surface was introduced.** Every new render site (`METRIC_LABELS`-backed titles, `formatMetricValue`/`formatTimestamp` output, spike-callout, insight-summary, `dashboardTitle` heading, Copy Link button) uses `textContent`/`createElement` exclusively — grepped the whole diff and `app.js` for `innerHTML`/`document.write`/`eval(` with zero hits outside a code comment.
- **No-leak error discipline holds in `generate.js`.** `generationFailed()` remains the single failure shape; `dashboardTitle` is omitted (not empty-stringed, not a distinct error) when invalid, matching D-08's existing lineage.

However, two BLOCKER-level functional defects were found by tracing the new insight-computation code against the real upstream data shapes and the retrieval-view DOM structure — both are silent failures (no error surfaced to the user, no console warning), which is exactly the kind of regression this phase's own "no-leak" convention is good at hiding from a code-only review.

## Critical Issues

### CR-01: `extractSeries()` can never parse the real `security-events` (DDoS) response shape — every security-events widget silently shows "Data unavailable," and this phase's own change is what makes that path reachable

**File:** `app.js:491-527` (also reachable via `app.js:19`)

**Issue:** `extractSeries()`'s only two recognized shapes are:
1. `data[0].TypeValue[]`/`data[0].FloatTypeValue[]` → `.Detail[]` (the function's own comment cites this as coming from `DescribeTimingL7AnalysisData`'s Output Parameters — i.e. the **CDN-traffic** action only), or
2. a flat array where `data[0].Time`/`.time` exists directly.

The real `DescribeDDoSAttackData` (security-events) response shape, verbatim-cited in this project's own `03-RESEARCH.md` (line ~392) as:
```json
{ "Response": { "Data": [
  { "Value": [ { "Max":100, "Metric":"...", "Avg":100, "Sum":100,
      "Detail": [ { "Timestamp":1660010100, "Value":100 } ] } ],
    "Key": "ddos_attackMaxBandwidth" } ] } }
```
has neither a `TypeValue`/`FloatTypeValue` key nor a top-level `Time`/`time` key on `data[0]` — it uses `Value`/`Key`. I traced this through a standalone Node reproduction using the exact shape from the research doc: `extractSeries()` returns `null` for it, unconditionally.

`renderChartWidget()`, `renderStatCardWidget()`, and `renderTableWidget()` all call `extractSeries()` first and return `renderPlaceholder(widget)` ("Data unavailable for this widget.") the moment it returns `null` — so **every widget type, for the security-events data source, always renders as a placeholder**, even though `/api/generate` successfully fetched real, non-empty `teoResponse.Response.Data` from `DescribeDDoSAttackData` server-side. This is a silent failure: no error banner, no distinct copy — it looks identical to a genuinely-empty-data case.

This bug's root cause (`extractSeries()` shape assumption) predates this phase (introduced in Phase 4 commit `69aeccb`), but **this phase is what makes it client-reachable**: `app.js:19`'s `getSourceFromUrl()` was widened this phase (commit `e52f2cc`, Task 1) from `value === 'cdn-traffic'` to `value === 'cdn-traffic' || value === 'security-events'`. Before this phase, there was no card/UI path setting `draft.dataSource = 'security-events'` and no URL-param acceptance either, so this dead code path was unreachable from the browser. This phase's own change opened the door to it while adding the very insight features (hero-metric, spike-callout, summary-insight) whose entire purpose is to make dashboards more interpretable — for this data source they can never render anything but "Data unavailable."

**Fix:** Add a third shape branch to `extractSeries()` handling `DescribeDDoSAttackData`'s `data[0].Value[].Detail[]` (note: `Value`, singular capital-V, is an array here, not a scalar):
```js
// DescribeDDoSAttackData shape: data[0].Value[].Detail[].{ Timestamp, Value }
const ddosDetail = Array.isArray(first?.Value) ? first.Value[0]?.Detail : undefined;
if (Array.isArray(ddosDetail) && ddosDetail.length > 0) {
  const series = ddosDetail
    .map((point) => {
      const rawTimestamp = point.Timestamp ?? point.Time ?? point.time;
      const label = formatTimestamp(rawTimestamp, interval);
      const value = Number(point.Value ?? point.value);
      return { label: String(label), value, rawTimestamp };
    })
    .filter((point) => !Number.isNaN(point.value));
  return series.length > 0 ? series : null;
}
```
Insert this check before or alongside the existing `TypeValue`/`FloatTypeValue` branch. Verify against a live `/api/data/security-events` (or `/api/generate` with `dataSource: "security-events"`) response, not just the cited doc shape, since this is exactly the kind of assumption Phase 4's own `69aeccb` fix commit shows was previously wrong for the CDN-traffic action too.

### CR-02: The retrieval view's "✓ Saved · Read-only" dashboard-state badge is coded to show but is structurally invisible — its own ancestor container is hidden

**File:** `app.js:941-942`, `app.js:965`, `index.html:605-609`

**Issue:** `renderRetrievalView()` hides the entire `.prompt-panel` container:
```js
const promptPanel = promptSection ? promptSection.querySelector('.prompt-panel') : null;
if (promptPanel) promptPanel.style.display = 'none';   // line 942
```
But per `index.html:605-609`, the `#dashboard-state-badge` span lives **inside** `.prompt-panel`:
```html
<div class="prompt-panel">
  <div class="prompt-panel-heading-row">
    <h2 id="prompt-panel-heading">Generate a dashboard</h2>
    <span id="dashboard-state-badge" class="dashboard-state-badge" style="display: none"></span>
  </div>
  ...
</div>
```
Later, on a successful fetch, `renderRetrievalView()` calls (line 965):
```js
setDashboardStateBadge('✓ Saved · Read-only', true);
```
`setDashboardStateBadge()` sets `badge.style.display = ''` on the badge element itself — but a `display: none` on an ancestor (`.prompt-panel`, set at line 942) removes the element and all its descendants from rendering regardless of the descendant's own `display` value. Nothing in `renderRetrievalView()` (or anywhere else) ever resets `.prompt-panel`'s display back to visible for the retrieval case. **The "✓ Saved · Read-only" badge can never actually be seen by a user in the retrieval view**, directly contradicting this phase's own `04.1-UI-SPEC.md` D-UI-17 ("the badge always reads '✓ Saved · Read-only' unconditionally on successful load") and Plan `04.1-02`'s own acceptance criteria / human-check script, which explicitly expects this badge to be visible in that view.

I confirmed via direct DOM-structure read that no other code path re-shows `.prompt-panel` for the retrieval branch — `dashboardMain`/`promptSection` are shown, but `promptPanel` itself stays hidden for the entire lifetime of that view.

**Fix:** Move the badge out of `.prompt-panel` (e.g. make it a sibling inside `#prompt-section`, or inside `#dashboard-main` directly, so it isn't nested under the element the retrieval view intentionally hides), or explicitly un-hide just the heading-row wrapper for the retrieval case:
```js
// In renderRetrievalView(), instead of hiding the whole .prompt-panel,
// hide only the textarea/button and leave the heading-row (h2 + badge) visible:
const textarea = promptSection?.querySelector('#prompt-textarea');
const genBtn = promptSection?.querySelector('#generate-btn');
if (textarea) textarea.style.display = 'none';
if (genBtn) genBtn.style.display = 'none';
```
Whichever approach is chosen, add a visual regression check (this is exactly the kind of bug automated `grep -c "dashboard-state-badge"` checks cannot catch, since the string exists in the file — it's a DOM-containment bug, not a missing-code bug).

## Warnings

### WR-01: `dashboardTitle` is silently dropped on Save and never appears in the retrieval view, even if the CSS containment bug (CR-02) is fixed

**File:** `app.js:12`, `app.js:846-849`

**Issue:** The client-side `draft` object (`app.js:12`) is `{ dataSource, prompt, spec, data }` — it has no `dashboardTitle` field. When the generate success branch runs, it updates `#prompt-panel-heading`'s `textContent` directly (line 798-804) but never assigns the validated title to `draft`. `saveDashboard()` (line 846-849) posts `{ spec: draft.spec, data: draft.data, prompt: draft.prompt }` to `/api/dashboard` — `dashboardTitle` is not in this payload, and `edge-functions/api/dashboard.js`'s stored record shape (`{ spec, data, prompt, createdAt }`) has no slot for it either. A user who generates a dashboard with a good LLM-supplied title, then saves and later reopens the bookmarked link, will never see that title again — even independent of CR-02, the data simply isn't persisted. This gap isn't called out anywhere in `04.1-CONTEXT.md`'s D-05/D-06 or the UI-SPEC as an intentional scope cut (D-06 discusses "no new backend routes" for Save/Preview polish generally, but doesn't discuss dropping `dashboardTitle` specifically).

**Fix:** Add `dashboardTitle: draft.dashboardTitle` to the `draft` object and the save payload, and include/return it from `dashboard.js`'s stored record and `dashboard/[id].js`'s response, so the retrieval view can render it (once CR-02 is fixed) as `body.dashboardTitle`. If this was an intentional v1 scope cut, it should at minimum be documented as such rather than left as an undocumented silent drop.

### WR-02: `formatMetricValue()` silently ignores its `unit` parameter for two of its five format rules, producing a subtly different unit string than `METRIC_LABELS` declares

**File:** `app.js:361-393`

**Issue:** `formatMetricValue(value, formatRule, unit)` takes a `unit` argument at every call site (looked up from `METRIC_LABELS[widget.metric].unit`), but the `ms-rounded` branch hardcodes `` `${Math.round(n)} ms` `` and the `rate-1dp` branch hardcodes `` `${n.toFixed(1)} req/s` `` — neither reads the passed-in `unit` string. This happens to match `METRIC_LABELS`'s current `ms`/`req per s` values closely enough not to visibly break today (`"req per s"` vs. the hardcoded `"req/s"` do differ slightly, so `l7Flow_requestRate`'s actual configured unit string is silently overridden), but it means the function's own contract (format value using the caller-supplied unit) is violated for 2 of 5 rules, and a future edit to `METRIC_LABELS`'s `unit` string for an `ms-rounded`/`rate-1dp` metric would have zero effect on the rendered output — a maintenance trap.

**Fix:** Either use the `unit` parameter consistently in all five branches, or drop the parameter for the two rules that don't need it and document why (e.g. "these two rules always render a fixed unit suffix by design, distinct from the generic bytes/bandwidth/integer rules").

### WR-03: `getSourceFromUrl()`'s widened acceptance of `security-events` has no corresponding UI entry point, so the only way to reach the still-broken code path (CR-01) is manually editing the URL

**File:** `app.js:14-20`, `index.html:592-602`

**Issue:** `index.html`'s data-source picker only renders a single `#card-cdn-traffic` card — there is no `security-events` card anywhere in the markup, and no click handler in `app.js` ever sets `draft.dataSource = 'security-events'` except via the URL param this phase's commit `e52f2cc` widened. This means the only way an end user reaches the `security-events` generation flow is by hand-editing `?source=security-events` into the URL — an unintentional, undocumented entry point into a data source with no picker card and (per CR-01) completely broken rendering. This isn't a security issue (the server still validates `dataSource` independently), but it's a half-finished feature surface that this phase's own change extended without adding the corresponding UI or fixing the rendering path it exposes.

**Fix:** Either add the missing `security-events` picker card (completing the feature) or revert the `getSourceFromUrl()` widening until `security-events` has both a UI entry point and working rendering (CR-01's fix).

## Info

### IN-01: `computeStats()`/`computeTrend()`/`detectSpike()` have no explicit empty-array guard, relying entirely on `extractSeries()`'s null-on-empty contract

**File:** `app.js:431-478`

**Issue:** `computeStats([])` produces `{ min: Infinity, max: -Infinity, avg: NaN }` (confirmed via direct execution) — none of these three functions guard against an empty `series` array themselves. Today this is safe only because every call site first checks `extractSeries()`'s return value for `null` (which it guarantees whenever the resulting series would be empty — `series.length > 0 ? series : null`), so an empty array is never actually passed to `computeStats`/`computeTrend`/`detectSpike` in practice. This is correct today, but it's an implicit cross-function contract (three call sites all coincidentally never violate it) rather than something these functions defend on their own — a future call site that skips `extractSeries()`'s null-check (e.g. a refactor, or a new caller) would silently render `"NaN"`/`"Infinity"` into the UI with no error.

**Fix:** Consider an explicit `if (series.length === 0) return null;` guard at the top of each of the three functions, making the "never called with an empty array" invariant self-enforcing rather than caller-dependent. Low priority given current call sites are safe, but worth hardening given these are exactly the kind of pure functions likely to be reused by a future insight feature.

### IN-02: `METRICS_BY_SOURCE[dataSource]`/`ACTION_BY_SOURCE[dataSource]` plain-object lookups are reachable with prototype-chain keys, though currently guarded before they matter

**File:** `edge-functions/lib/generation-schema.js:100-105`, `edge-functions/api/generate.js:158-161`

**Issue:** `METRICS_BY_SOURCE` and `ACTION_BY_SOURCE` are plain `{}` object literals (not `Object.create(null)` or a `Map`), so a `dataSource` value of `"__proto__"` or `"constructor"` resolves truthy (`!METRICS_BY_SOURCE['__proto__']` is `false`, since the lookup returns the object's own prototype/constructor rather than `undefined`) — confirmed via direct execution against the real `generation-schema.js` module. In `generate.js`, the guard `if (!METRICS_BY_SOURCE[dataSource]) return generationFailed();` would NOT reject `dataSource: "__proto__"`, and the very next line, `buildSystemPrompt(dataSource, previousSpec)`, calls `METRICS_BY_SOURCE[dataSource].join(', ')` inside itself (`metrics.join(...)` where `metrics = METRICS_BY_SOURCE[dataSource] || []`) — since `METRICS_BY_SOURCE['__proto__']` is an object (not an array, not falsy), `.join` doesn't exist on it, throwing `TypeError: metrics.join is not a function`. This would surface as an unhandled exception in the Edge Function (not a graceful `generationFailed()`), which is a violation of this file's own no-leak/never-throw convention for a malformed/adversarial `dataSource` value, though the actual worker-level error response is still expected to be generic per the platform's own crash handling (not a data leak, just a robustness gap). This is a pre-existing pattern from Phase 4 (not introduced this phase), flagged here only because `generation-schema.js` was in this review's scope and the guard is adjacent to this phase's own new `validateDashboardTitle()` addition.

**Fix:** Either validate `dataSource` against `Object.keys(METRICS_BY_SOURCE)` explicitly (rejecting inherited-property matches), or use `Object.hasOwn(METRICS_BY_SOURCE, dataSource)` in the guard at `generate.js:158`, e.g.:
```js
if (!Object.hasOwn(METRICS_BY_SOURCE, dataSource)) {
  return generationFailed();
}
```
