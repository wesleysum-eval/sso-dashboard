# Phase 4.1: Dashboard Renderer & Insights Polish - Context

**Gathered:** 2026-08-13 (live conversation, following user feedback that the Phase 4 dashboard is "hard to interpret")
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 4 (complete, all 5 requirements live-verified) proved the end-to-end prompt -> generate -> refine -> save -> retrieve pipeline works. This phase does not touch that pipeline's trust boundaries — it fixes the **rendering/display layer** so the resulting dashboard is actually readable and useful, and adds a small amount of **computed** (not LLM-invented) insight surfacing on top of already-fetched data.

This phase does **not** reopen GEN-03's constrained-generation security model. The Anthropic-Artifacts-style "let the LLM generate freeform HTML/JS" idea was explicitly explored and rejected this session — see Decisions below.

</domain>

<decisions>
## Implementation Decisions

### Root cause of "hard to interpret" (diagnosed this session, not speculative)
- **D-01:** Confirmed via code read of `app.js`/`generation-schema.js`: the "hard to understand / real ID getting triggered" complaint is caused by (a) `app.js`'s `widgetCardShell()` falling back to `widget.metric` (the raw `teo` API code, e.g. `l7Flow_outFlux`, `ddos_attackMaxBandwidth`) as the widget title whenever the LLM's `title` field is weak/empty, and (b) there being no human-readable label/unit lookup anywhere in the codebase — `generation-schema.js`'s `METRICS_BY_SOURCE` only has raw `teo` metric codes, no display names or units (MB/GB/bps/ms/qps). Timestamps in `extractSeries()` also pass through as raw `point.Time` strings with no date formatting.
- This is **not** a missing-system-prompt problem — `generate.js`'s `buildSystemPrompt()` already exists and is reasonably well-structured (closed enums spelled out, JSON-only instruction, retry-once-on-malformed-JSON). Confirmed by direct code read, not assumption.

### Rejected direction: Anthropic Artifacts-style freeform HTML generation
- **D-02:** [Explored and rejected] User asked whether the LLM should generate raw HTML/CSS/JS (like Claude.ai Artifacts) to render the dashboard, inspired by Workbuddy's "AI writes an HTML file" pattern. Rejected because it directly reverses Phase 4's locked, one-way decisions (`04-CONTEXT.md` D-01/D-02/D-03, `PROJECT.md` Constraints: "AI dashboard generation should be constrained... rather than arbitrary open-ended code generation"). Freeform LLM-generated JS rendered in a sandboxed iframe does not by itself prevent tenant-data exfiltration via `fetch()` calls unless paired with CSP-level network lockdown — reopens exactly the injection/exfil risk the fixed vocabulary exists to prevent. **This boundary remains locked; do not revisit without a deliberate, explicit new decision.**
- **D-03:** [Adopted instead] Where richer output is wanted (hero metric, spike callout, summary insight, trend framing), compute it **server-side or client-side from already-fetched, already-validated data** — never let the LLM freely invent new widget/output types at generation time. This keeps the same trust boundary GEN-03 already established: the LLM only ever selects from closed enums; a human/deliberate decision (not a runtime prompt) is what would ever expand the rendering vocabulary (per D-01 in `04-CONTEXT.md`, "one-way — expanding this list is a deliberate future decision, not something a prompt can trigger at runtime").

### Scope for this phase (user-proposed 3-item plan, refined this session)
- **D-04:** **Better Dashboard Renderer.** Fix the root cause (D-01): add a `METRIC_LABELS` lookup (metric code -> `{ label, unit }`) alongside `METRICS_BY_SOURCE` in `generation-schema.js`; fix `widgetCardShell()`'s title fallback to use the human label instead of the raw metric code; format timestamps in `extractSeries()`/render functions instead of raw ISO strings; add units to displayed values (stat-card, table, chart tooltips). Additionally add a small set of **computed** (not LLM-generated) insight elements layered on top of existing chart/stat-card widgets: hero/primary metric emphasis, a simple spike callout (statistical threshold check over an already-fetched series — e.g., a point exceeding N standard deviations or 2x rolling average), and a short templated summary-insight string built from computed stats (min/max/avg/trend direction) — not new LLM-invented widget types, not freeform text generation.
- **D-05:** **Prompt Refinement — rejected as a separate LLM stage.** User proposed a second "refine intent" LLM call to turn vague prompts ("show traffic") into structured intent before generation. Rejected as its own pipeline stage: doubles LLM round-trips (cost + latency + a second failure point) for marginal benefit. Adopted instead: add one more free-text, display-only field (`dashboardTitle`) to the *existing* single generation call's schema — validated identically to how `widget.title` is already validated (free-text, capped length, never used to construct a query, per `04-CONTEXT.md`'s existing precedent) — giving the dashboard an overall human-readable title without a new LLM call.
- **D-06:** **Save/Preview mode UI polish.** Phase 4 Plan 02 already built Save (returns bookmarkable link) and a read-only retrieval view. This phase's contribution is UI polish only: add an explicit "Copy Link" affordance (clipboard write) next to the existing bookmarkable link, and clearer visual state labeling between "generating," "viewing live draft," and "viewing saved/read-only dashboard." No new backend routes — `edge-functions/api/dashboard.js` and `edge-functions/api/dashboard/[id].js` (Phase 4 Plan 02) are reused unchanged.

### Relationship to existing backlog item
- **D-07:** `ROADMAP.md`'s Backlog already contains "Phase 999.1: Predefined dashboard templates," whose **Template 3 (Traffic Spike Detection)** independently proposes a `derivedLogic` field (`max_point_vs_rolling_average`, `highlight_points_over_2x_average`, `list_points_over_threshold`) — this is the same computation this phase's spike-callout (D-04) needs. When planning, check whether Template 3's `derivedLogic` design should be pulled forward/reused here rather than re-designed from scratch, to avoid two divergent spike-detection implementations.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `edge-functions/lib/generation-schema.js`: `METRICS_BY_SOURCE` already has the full, real `teo` MetricNames enum per data source (10 CDN metrics, 4 security metrics) — the human-readable meaning of each is already documented as inline comments in `04-RESEARCH.md` (lines ~106-129, e.g. "L7 EdgeOne response traffic (Byte)") and can be lifted directly into the new `METRIC_LABELS` lookup without new research.
- `app.js`'s `extractSeries()` already normalizes multiple plausible `teo` response shapes into a flat `[{ label, value }]` series — the natural place to add timestamp formatting and unit-aware value formatting.
- Chart.js (CDN-loaded, already in `index.html`) already renders line/bar charts — no new charting dependency needed for hero-metric/spike-callout treatment (can be plain HTML/CSS annotations over existing chart output).

### Established Patterns
- Closed-enum validation (`validateWidget()` in `generation-schema.js`) is the existing pattern any new schema field (`dashboardTitle`) must follow: validate the type/length, never trust/execute the LLM's raw string for anything beyond display.
- No-leak generic error convention (D-08 lineage) — any new failure branch this phase introduces (e.g., a malformed `dashboardTitle`) must degrade gracefully (e.g., fall back to a default title), not surface a distinct new error state.

### Integration Points
- `edge-functions/lib/generation-schema.js` — add `METRIC_LABELS` export, extend `validateWidget()`'s return shape if `dashboardTitle` is validated at the widget-array level rather than per-widget (planning to determine exact shape).
- `edge-functions/api/generate.js` — `buildSystemPrompt()` gains one more line describing `dashboardTitle` if D-05 is implemented; response assembly includes it.
- `app.js` — `widgetCardShell()` title fallback, `extractSeries()` timestamp/value formatting, new hero-metric/spike-callout/summary-insight rendering functions, "Copy Link" button in the existing Save UI.
- `index.html` — CSS for any new insight/hero-metric visual treatment (reuse existing `:root` tokens only, per `04-UI-SPEC.md`'s zero-new-token contract already established in Phase 4).

</code_context>
