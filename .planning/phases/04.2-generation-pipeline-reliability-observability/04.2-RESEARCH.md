## Summary

This phase closes four gaps between `04-AI-SPEC.md`'s design and Phase 4's actual shipped code, in the priority order CONTEXT.md D-05 locks: (1) parallelize `generate.js`'s per-widget `teo` fetch loop with `Promise.allSettled()`, (2) add a `requestedCount`/`validCount` field to `/api/generate`'s response, (3) add structured `console.log(JSON.stringify({...}))` calls at the exact points `04-AI-SPEC.md` Section 7 already specifies, (4) stand up a `evals/` directory with Promptfoo per `04-AI-SPEC.md` Section 5's already-designed dimensions/dataset/tooling choice.

None of these four items require new architectural decisions — `04-AI-SPEC.md` already designed all four (Sections 4b.2, 1b/Known-Failure-Mode-#4, 7, and 5 respectively), so this research validates that design against current tool behavior and the actual current `generate.js` code, rather than re-deriving anything. The one genuinely new finding this session: **EdgeOne's edge runtime enforces a hard 8-concurrent-fetch cap and a 64-total-fetch cap per single function execution** — both far above this pipeline's realistic 1-4 widget count, so `Promise.allSettled()` is safe with zero further mitigation needed. The second genuinely new finding: **the `promptfoo` npm package registry lookup returns a `SUS` verdict** (reason: `too-new`, `publishedAt: 2026-08-04`) from this session's automated legitimacy check, which contradicts `npm view promptfoo time.created` (`2023-05-03`) and 630K weekly downloads — almost certainly a registry-metadata artifact (possibly a recent major-version republish or mirror timestamp), but per this project's own package-legitimacy protocol it must still be flagged `[SUS]` and gated behind a `checkpoint:human-verify` before install, not silently waved through on the strength of the other signals.

**Primary recommendation:** Implement D-03/D-04/D-02/D-01 in CONTEXT.md's locked priority order. For D-03, replace the `for...await` loop in `generate.js` with a `.map()` over `validWidgets` producing an array of per-widget async functions, run through `Promise.allSettled()`, and filter `status === 'fulfilled'` results — preserving the existing per-widget `try/catch`+`continue` isolation logic essentially unchanged, just moved from loop-body-with-continue into a per-widget async function that returns `null` on failure instead of `continue`-ing.

### Pattern 1: Promise.allSettled() with preserved per-widget try/catch isolation

**What:** Convert the sequential `for...await` loop into a `.map()` producing promises, awaited via `Promise.allSettled()`, filtering for successful results.

**When to use:** Any set of independent async operations where one failure must never abort siblings — exactly this codebase's existing Pitfall 6 discipline.

**Example — current code (sequential, the bug):**
```javascript
// edge-functions/api/generate.js, current shipped code (lines 217-260)
const widgets = [];
for (const widget of validWidgets) {
  const { startTime, endTime } = computeTimeRangeWindow(widget.timeRange);
  const { url, headers, body: signedBody } = await signTeoRequest({ /* ... */ });
  let teoResponse;
  try {
    const res = await fetch(url, { method: 'POST', headers, body: signedBody });
    teoResponse = await res.json();
  } catch {
    continue; // Pitfall 6: per-widget failure, not per-request
  }
  if (teoResponse?.Response?.Error) { continue; }
  widgets.push({ componentType: widget.componentType, title: widget.title, metric: widget.metric, interval: widget.interval, timeRange: widget.timeRange, data: teoResponse?.Response?.Data });
}
```
`[VERIFIED: edge-functions/api/generate.js:217-260]` — this is the exact code this phase's D-03 replaces.

**Recommended fix — concurrent, same isolation semantics:**
```javascript
// generate.js — D-03 fix. Each widget's fetch becomes a self-contained async
// function that NEVER throws out of Promise.allSettled's array — it catches
// its own failure and returns null, exactly mirroring the current `continue`
// semantics but as a return value instead of a loop-control statement.
async function fetchWidgetData(widget, account, action, version, env) {
  const { startTime, endTime } = computeTimeRangeWindow(widget.timeRange);
  const { url, headers, body: signedBody } = await signTeoRequest({
    secretId: account.secretId,
    secretKey: account.secretKey,
    action,
    version,
    payload: {
      StartTime: toTeoRfc3339(startTime),
      EndTime: toTeoRfc3339(endTime),
      MetricNames: [widget.metric],
      Interval: widget.interval,
      ZoneIds: [account.zoneId],
    },
    domain: env.TEO_API_DOMAIN,
  });

  let teoResponse;
  try {
    const res = await fetch(url, { method: 'POST', headers, body: signedBody });
    teoResponse = await res.json();
  } catch {
    // Pitfall 6, preserved: this widget's failure never propagates.
    return null;
  }

  if (teoResponse?.Response?.Error) {
    // Never forward Response.Error — it can contain the ZoneId (03-RESEARCH.md Pitfall 5).
    return null;
  }

  return {
    componentType: widget.componentType,
    title: widget.title,
    metric: widget.metric,
    interval: widget.interval,
    timeRange: widget.timeRange,
    data: teoResponse?.Response?.Data,
  };
}

// D-03: concurrent instead of sequential — the only structural change.
// Note fetchWidgetData() itself never rejects (it catches internally and
// returns null), so every entry in `settled` will have status:'fulfilled'
// in practice; the .filter(Boolean) after unwrapping .value is what
// actually drops the null (failed) widgets. Promise.allSettled is still
// the correct choice over Promise.all — even though fetchWidgetData()
// doesn't reject today, allSettled makes the pipeline resilient to a
// FUTURE bug where someone adds a throwing branch inside fetchWidgetData
// without remembering to catch it there too (defense in depth, not just
// today's correctness).
const settled = await Promise.allSettled(
  validWidgets.map((widget) => fetchWidgetData(widget, account, action, version, env)),
);
const widgets = settled
  .filter((r) => r.status === 'fulfilled' && r.value !== null)
  .map((r) => r.value);
```
`[VERIFIED: developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/allSettled — return shape confirmed: array of {status:'fulfilled', value} | {status:'rejected', reason}, in input order regardless of completion order]`

**Why `Promise.allSettled` over `Promise.all` here specifically:** `04-AI-SPEC.md` Section 4b.2 already made this exact call `[CITED: 04-AI-SPEC.md Section 4b.2]`: *"since each widget's fetch is already independently no-leak/fail-soft (Pitfall 6...), Promise.allSettled() is actually the more correct choice so one rejected promise doesn't reject the whole batch."* Even though `fetchWidgetData()` above catches its own errors internally (so in practice no promise ever rejects), keeping `allSettled` rather than downgrading to `all` is the safer long-term choice — a future edit to `fetchWidgetData()` that accidentally removes the inner `try/catch` would silently reintroduce the all-or-nothing bug under `Promise.all()`, whereas `Promise.allSettled()` degrades gracefully either way.

### Anti-Patterns to Avoid
- **`Promise.all()` for this loop:** rejects the entire batch on the first widget's fetch failure — reopens Pitfall 6, converts partial-success into total failure for reasons unrelated to the LLM's output quality (e.g., one transient `teo` timeout would blank the whole dashboard).
- **Firing all N fetches with no `Promise.allSettled`/`Promise.all` wrapper at all (bare `.map()` with no `await Promise.allSettled(...)`)**: this does NOT actually wait for the fetches — `.map()` returns an array of pending promises immediately, and the function would return before any `teo` data arrived. The `await Promise.allSettled(...)` wrapper is not optional.
- **Assuming `signTeoRequest()` needs to be excluded from the parallelized function**: it's an independent, stateless, per-widget signing call (a fresh HMAC over that widget's own payload) — it belongs inside the per-widget async function, not hoisted out, exactly as shown in Pattern 1 above.

## Common Pitfalls

### Pitfall 1: Converting the loop to `.map()` without wrapping in `Promise.allSettled`/`await`
**What goes wrong:** `validWidgets.map(w => fetchWidgetData(...))` alone returns an array of Promise objects instantly; if the code proceeds to build the response from that array without `await`ing it first, every widget's `data` field will be `undefined` (or the response will contain unresolved Promise objects that fail to `JSON.stringify` meaningfully).
**Why it happens:** `.map()` is synchronous by definition — it does not wait for async callbacks to resolve.
**How to avoid:** Always structure as `const settled = await Promise.allSettled(validWidgets.map(...))`, exactly as shown in Pattern 1.
**Warning signs:** Widget `data` fields render as `undefined`/blank in the client, or a `TypeError` when the code tries to read `.value`/`.data` off something that's still a pending Promise.

### Pitfall 2: `requestedCount` computed from the wrong array
**What goes wrong:** D-04's count signal is meant to answer "how many widgets did the LLM propose vs. how many survived validation AND the real teo fetch" — but there are actually three candidate counts in the pipeline (`candidates.widgets.length` — raw LLM output before any validation; `validWidgets.length` — after `validateWidget()` but before the teo fetch; `widgets.length` — after both validation AND a successful teo fetch). Picking the wrong pair to expose could either overstate transparency (showing "4 of 4" when 2 later failed their teo fetch silently) or understate it.
**Why it happens:** `04-AI-SPEC.md`'s own Section 1b Known Failure Mode #4 and Section 5's rubric both frame this specifically as "widgets requested vs widgets generated" — i.e., the LLM's proposal count vs. what actually rendered, which means the correct pair is `candidates.widgets.length` (requestedCount) vs. `widgets.length` (validCount, post-teo-fetch) — NOT `validWidgets.length`, which is an intermediate value the user never sees rendered or not-rendered.
**How to avoid:** `requestedCount = candidates.widgets.length` (or `.length` guarded for the case where `candidates.widgets` isn't an array, though that branch already returns `generationFailed()` before this point); `validCount = widgets.length` (the final post-teo-fetch array, after the `Promise.allSettled` fix in Pattern 1).
**Warning signs:** A widget that validated schema-wise but failed its `teo` fetch (e.g., a transient network error) would be miscounted as "generated" if `validCount` is taken from `validWidgets.length` instead of the final `widgets.length` — silently reintroducing exactly the transparency gap D-04 exists to close, just one step later in the pipeline.

### Pitfall 3: Logging the wrong things per D-08's no-leak convention
**What goes wrong:** `04-AI-SPEC.md` Section 7's log event shape explicitly lists what must NEVER be logged (`raw prompt text, raw LLM content, MAKERS_MODELS_KEY, dashboard data values`) — but a naive implementation might log `JSON.stringify({...candidates})` for debugging convenience, which would include the raw LLM response including any widget titles (free text, potentially reflecting injected prompt content) and metric values.
**Why it happens:** `console.log(JSON.stringify(candidates))` is a natural, fast way to debug "what did the LLM actually return" during development — but that same line left in production code becomes a standing no-leak violation, and per this project's D-08 lineage this is treated as a Critical-severity bug category (see `04-AI-SPEC.md` Section 7's own "should never fire" framing).
**How to avoid:** The log event shape's own explicit "NEVER logged" comment line, copied verbatim into the actual code as a comment above each `console.log` call in `generate.js`/`dashboard.js`/`dashboard/[id].js`, so the constraint is visible at every call site, not just in the design doc.
**Warning signs:** A `grep -rn "console.log" edge-functions/` audit finding any log statement whose argument object includes `prompt`, `content`, `secretKey`, `MAKERS_MODELS_KEY`, or a widget's `data` field by name.

### Pitfall 4: Promptfoo's `SUS` legitimacy verdict being silently ignored because the surrounding evidence looks fine
**What goes wrong:** A planner or executor sees `npm view promptfoo` returning a real, well-established, high-download package and concludes the automated `SUS` flag from this session's `package-legitimacy check` was simply wrong, then installs it without the required `checkpoint:human-verify` gate.
**Why it happens:** The seam's `too-new` signal appears to be keyed to the *latest version's* publish timestamp (a fast-moving weekly-release project will always look "new" by that heuristic) rather than the *package's* actual founding date — a real methodological gap in the seam, not a signal about this specific package being fake.
**How to avoid:** Follow the protocol as written regardless of how confident the other signals make you feel — insert the `checkpoint:human-verify` task before `npm install --save-dev promptfoo` per the Package Legitimacy Audit section above. The gate is cheap (a human confirms the installed `node_modules/promptfoo/package.json`'s repository field matches `github.com/promptfoo/promptfoo`) and the cost of skipping it once, on a genuinely slopsquatted package, is unbounded.
**Warning signs:** None specific to this package — this is a process discipline pitfall, not a code pitfall.

### Pitfall 5 (carried forward, re-confirmed this session): EdgeOne's fetch concurrency ceiling is NOT a concern for this fix, but the CPU-time budget IS worth knowing
**What goes wrong:** A future widget-count increase (e.g., allowing the LLM to propose more than 4 widgets) could eventually approach EdgeOne's documented per-invocation limits.
**Why it happens:** EdgeOne Edge Functions enforce (per official docs, confirmed live this session): max **64 total `fetch()` calls** per single function execution (exceeding this throws), max **8 concurrent in-flight fetches** per execution (calls beyond 8 queue until a slot frees — they are delayed, not rejected outright), and a **200ms CPU-time budget** for the whole invocation (explicitly excluding I/O wait time). `[VERIFIED via web fetch this session: cloud.tencent.com/document/product/1552/81897, "运行时限制" section, updated 2025-11-10 — quoted: "边缘函数单次运行中可发起的 fetch 总次数为 64" / "边缘函数单次运行中允许发起 fetch 最大并发数为 8" / default timeout "15秒", max "300秒"]`
**How to avoid:** For this phase's fixed 1-4 widget range (per `generation-schema.js`'s system prompt: `'Return between 1 and 4 widgets'`), 4 concurrent `teo` fetches is nowhere near the 8-concurrency or 64-total ceiling — no mitigation needed. **Flag for future reference only:** if a later phase raises the widget cap materially (e.g., to 10+), the 8-concurrent ceiling would start to matter (calls 9+ would queue rather than fail, adding latency back for the "excess" widgets — a soft-degrade, not a hard failure). The 200ms CPU-time budget excludes I/O wait, so waiting on `teo` network round-trips doesn't consume it — only synchronous JS execution (JSON parsing, HMAC signing math) counts against the 200ms, and this pipeline's synchronous work per widget is trivially small.
**Warning signs:** None expected at this phase's scope — noted purely so the planner doesn't need to re-research this if the widget cap ever changes later.

## Open Questions

1. **Should `requestedCount`/`validCount` be included in EVERY `/api/generate` response, or only when they differ?**
   - What we know: D-04's rubric (Section 5, "Partial-success transparency") only requires the signal to exist "whenever `widgets.length < candidates.length`" — it doesn't explicitly require the fields on a full-success response too.
   - What's unclear: whether omitting the fields on a full-success response (matching the existing `dashboardTitle`-only-when-valid convention) or always including them (simpler client logic: `if (validCount < requestedCount) show banner`) is preferred.
   - Recommendation: Always include both fields (simpler, consistent response shape, trivial extra payload size) — this avoids the client needing to distinguish "field absent" from "field present and equal," which is a subtler client-side bug surface than the minor extra bytes cost. Planning should confirm this against D-04/D-05's "server-only is fine, client surfacing is optional" framing.

2. **Does the `checkpoint:human-verify` gate for `promptfoo`'s SUS verdict block ALL of D-01, or just the `npm install` step?**
   - What we know: the SUS verdict is specifically about the *install-time* package-identity check; the eval suite's *design* (config format, assertion patterns, reference dataset) can be fully planned and even authored (YAML/JS files written) without the package being installed yet.
   - What's unclear: whether planning should sequence D-01's tasks so all non-install work (writing `evals/testcases.yaml`, `evals/assertions/*.js`, `evals/promptfooconfig.yaml`) happens before the `checkpoint:human-verify`-gated `npm install` step, allowing the human-verify gate to be the LAST blocking step of D-01 rather than the first.
   - Recommendation: Sequence `npm install --save-dev promptfoo` behind a `checkpoint:human-verify` task, but let all other `evals/` authoring happen in parallel/before it — the eval config files don't need the package installed to be written correctly, only to be *run*.
