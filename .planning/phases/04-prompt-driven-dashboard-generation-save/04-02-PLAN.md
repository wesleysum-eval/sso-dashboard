<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> /api/dashboard (save) | Only the verified session cookie determines which tenant's KV namespace-prefix the write lands under; the client-supplied `spec`/`data`/`prompt` body fields are stored as-is (already-validated widget data and free-text — no further scoping risk since they were validated at generation time). |
| Browser -> /api/dashboard/:id (retrieve) | The URL's `id` segment is client-controlled and untrusted; `tenant_id` is never read from it — only from the verified session, per D-06. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-05 | Elevation of Privilege / Information Disclosure | edge-functions/api/dashboard/[id].js | critical | mitigate | The KV key requires BOTH the session-derived `tenant_id` AND the URL's `dashboard_id` to match; an attacker with a valid session for tenant A who guesses/enumerates tenant B's `dashboard_id` still fails, because their own session resolves tenant A's prefix, not tenant B's — re-verified via the explicit negative test in Task 3 step 5. |
| T-04-06 | Information Disclosure | edge-functions/api/dashboard/[id].js failure branch | high | mitigate | "Missing key" and "wrong tenant" return the byte-identical `{ error: 'not_found' }` response — no timing or content difference that could let an attacker distinguish "doesn't exist" from "exists but isn't mine" (D-06). |
| T-04-07 | Spoofing | edge-functions/api/dashboard.js, dashboard/[id].js (unauthenticated access) | high | mitigate | `verifySession()` is the first branch in both files, before any KV call — identical pattern to every other route in this codebase. |
| T-04-08 | Tampering | Client-side draft state (`app.js` `draft` object) | low | accept | The re-prompt draft lives only in the browser's JS memory, never persisted server-side; tampering with it client-side can at worst cause a malformed `/api/generate` request, which the server validates identically to any other request (no elevated trust granted to `previousSpec`). |

</threat_model>
