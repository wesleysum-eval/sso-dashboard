# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Auto mode note:** No live user available for this session. All new UI decisions below are Claude-selected recommended defaults, tagged `[auto] D-UI-XX`, following the same auto-mode convention `04-CONTEXT.md`/`03-CONTEXT.md` already use (`[auto] D-01`..`D-08`). Numbered `D-UI-XX` (not `D-01..D-08`) to avoid colliding with `04-CONTEXT.md`'s existing decision IDs, which this document extends rather than repeats.

**Scope note:** Phase 4 adds four UI surfaces to the existing single-page app (`index.html`/`app.js`): (1) a prompt input + Generate control, gated behind Phase 3's selected data source, (2) a generated-dashboard render area for the four fixed widget types (`line-chart`, `bar-chart`, `stat-card`, `table` — locked by `04-CONTEXT.md` D-01), (3) a re-prompt/Regenerate control that refines the same render area without navigating away (D-07), and (4) a Save control plus a read-only retrieval view (`/?dashboard=<id>`). No dashboard list/history UI exists this phase (SHARE-02 is v2) — retrieval is "revisit the exact saved link," not "browse my dashboards."

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 (regular) | 1.5 |
| Label | 13px | 400 (regular) | 1.4 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

Only two weights in use for **new Phase 4 elements**: 400 and 600 — matching Phase 2's original two-weight rule exactly.

**Carry-forward caveat (not a new decision, flagged for awareness):** the *existing* shipped `index.html`/`app.js` (Phase 2/3) drifted to also use `500` (`.tenant-badge`) and `700` (`.login-card h1`, `.navbar-brand`, `.dashboard-main h2`) during the user's manual page-structure rebuild (see `02-UI-SPEC.md` Design System note). This document does not re-litigate that existing drift or ask the executor to fix it retroactively — it only constrains **new** Phase 4 elements to the clean 400/600 pair below, reusing the sizes/weights that already exist where a direct match is available (e.g. `.source-card-title` is already 15px/600 — closest existing analog to "Heading" role; new widget-card titles should reuse that exact existing style rather than introducing a third heading size).

**Phase 4 usage:**
- Heading (20px/600) → "Generate a dashboard" section title (reuses `.dashboard-main h2`'s existing 20px size, drops its existing 700 weight to 600 for new elements per the two-weight rule above); widget-card title text (reuses `.source-card-title`'s pattern — 15px/600 is the closer existing match for a *smaller* card-header title; use 15px/600 for widget-card titles specifically, 20px/600 for the page-level section heading only — both are the same 600 weight, just two of the four declared sizes are size-reused from existing CSS)
- Body (14px/400) → prompt textarea text, widget table cell text, error/empty state body copy (reuses existing `.section-subtitle`/`.source-card-desc` size exactly)
- Label (13px/400) → widget meta text (e.g. "Last 7 days · Hourly"), save-confirmation timestamp, chart axis captions (reuses existing `.result-panel`/`.source-card-desc` 13px size exactly)
- Display (28px/600) → the single large number inside a `stat-card` widget — new size, needed for visual hierarchy; nothing existing plays this role today

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (initial) | **"Generate Dashboard"** — button label before any dashboard has been generated yet |
| Primary CTA (after first generation) | **"Regenerate"** — same button, relabeled once a dashboard already exists, submitting the re-prompt textarea's contents (GEN-04) |
| Save CTA | **"Save Dashboard"** |
| Prompt input placeholder | **"e.g. Show me traffic trends over the last 7 days"** |
| Empty state heading | **"No dashboard yet"** |
| Empty state body | **"Describe what you want to see, then generate to build your dashboard."** |
| Loading state (generate/regenerate) | **"Generating…"** — button label while `/api/generate` is in flight; button is disabled during this state |
| Loading state (save) | **"Saving…"** — button label while `POST /api/dashboard` is in flight; button is disabled during this state |
| Loading state (retrieve) | **"Loading dashboard…"** — shown in place of the widget stack while `GET /api/dashboard/:id` resolves |
| Error state (generation failure) | **"Couldn't generate a dashboard from that prompt — try rephrasing."** — verbatim from `04-CONTEXT.md`/`04-RESEARCH.md` D-08/D-03 step 4; this exact string, no variation, regardless of failure cause (malformed JSON, zero valid widgets, LLM timeout) |
| Error state (save failure) | **"Couldn't save right now. Try again in a moment."** — matches the D-08 no-leak convention (no raw KV/API error detail) |
| Error state (retrieve / not found) | **"Dashboard not found."** — shown for both a missing `dashboard_id` and a cross-tenant retrieval attempt (D-06); never varies by cause, matching the access-denied page's same-copy-regardless-of-cause precedent from `02-UI-SPEC.md` |
| Widget-level data-unavailable | **"Data unavailable for this widget."** — shown inside a single widget card when that widget's own `teo` fetch failed, while sibling widgets in the same dashboard render normally (Pitfall 6) |
| Save success confirmation | **"Dashboard saved. Bookmark this link to view it again:"** followed by the retrievable URL (`/?dashboard=<id>`) rendered as a link — per Pitfall 5, this confirmation renders from the already-in-memory save response, never from an immediate re-fetch |
| Destructive confirmation | Not applicable — Phase 4 has no destructive actions (no delete, no logout; matches `02-UI-SPEC.md`'s same finding for Phase 2). |

**Hard constraints carried from `04-CONTEXT.md`/`04-RESEARCH.md`:**
- The generation-failure copy must never vary based on the underlying cause (D-08) — always the exact string above.
- The retrieve-failure copy must never distinguish "doesn't exist" from "belongs to another tenant" (D-06) — always "Dashboard not found."
- The LLM's free-text `title` field is rendered via `textContent`/`createElement` only, never `innerHTML` (Anti-Patterns, XSS mitigation) — this applies to every widget-title render site.

## Component & Layout Notes

> Extra implementation-facing detail beyond the standard template sections, because this phase introduces genuinely new layout (no existing analog for a multi-widget dashboard render area).

New CSS class contracts for the executor to implement, all extending `index.html`'s existing single `<style>` block:

| Class | Purpose |
|-------|---------|
| `.prompt-panel` | Container for the textarea + Generate/Regenerate button, sits below the (Phase 3) data-source `.card-grid`, `--space-xl` (32px) top margin, reuses `.result-panel`'s card surface styling (white, border, `--radius-md`) |
| `.prompt-textarea` | The prompt input itself — full width of `.prompt-panel`, 14px/400 body text, min-height ~2 lines |
| `.widget-stack` | Vertical single-column layout for rendered widgets (D-UI-04) — **not** a grid; each widget card is full-width of `.dashboard-main`'s existing 960px max-width container, `--space-md` (16px) gap between stacked cards |
| `.widget-card` | One card per widget — reuses `.source-card`'s existing surface treatment (white, `--color-border`, `--radius-md`, `--shadow-card` on hover is **not** needed here since widgets aren't clickable) |
| `.widget-card-title` | 15px/600 (reuses `.source-card-title`'s exact existing size/weight) — truncates with ellipsis per D-UI-05 |
| `.widget-placeholder` | Modifier/state on `.widget-card` for the per-widget data-unavailable state (Pitfall 6) — same card chrome, muted `--color-text-muted` body text, no chart canvas rendered |
| `.stat-card-value` | 28px/600 Display-role text, used only inside a `componentType: 'stat-card'` widget |
| `.save-bar` | Container below `.widget-stack` holding the Save button and, after success, the save-confirmation copy + retrievable link |
| `.error-banner` | Inline banner shown above `.widget-stack` on a regenerate failure (D-UI-01) — does not replace/clear the existing widget stack beneath it |

| Category | Element(s) | Status | Resolution / Reason |

| empty | `.widget-stack` (pre-generation) | ✅ covered | Before any generation, `.widget-stack` shows the "No dashboard yet" heading + body from Copywriting Contract above, not an empty/blank container. |
| loading | Generate/Regenerate button | ✅ covered | Button label switches to "Generating…" and disables itself for the duration of the `/api/generate` request; `.widget-stack` content (if any, from a prior successful generation) remains visible underneath per D-UI-01. |
| loading | Save button | ✅ covered | Button label switches to "Saving…" and disables itself for the duration of the `POST /api/dashboard` request. |
| loading | Retrieval view (`/?dashboard=<id>`) | ✅ covered | Shows "Loading dashboard…" text in place of `.widget-stack` while `GET /api/dashboard/:id` resolves. |
| error | Generate/Regenerate | ✅ covered | **[auto] D-UI-01:** On failure, the last successfully rendered dashboard (if any) stays visible in `.widget-stack`; a `.error-banner` with the exact D-08 copy appears above it. On the very first generation attempt (no prior dashboard), the empty state is replaced by the error banner alone. |
| error | Save | ✅ covered | Button re-enables, label reverts to "Save Dashboard", and the generic save-failure copy appears in `.save-bar` — the just-generated dashboard in `.widget-stack` is untouched. |
| error | Retrieval view | ✅ covered | Full-page "Dashboard not found." state, styled consistent with Phase 2's centered-card access-denied pattern (`02-UI-SPEC.md`) — same copy regardless of cause (missing ID vs. cross-tenant, per D-06). |
| populated | `.widget-stack` | ✅ covered | Renders 1–N widgets from the validated spec, each as its own `.widget-card` using one of the four fixed types (D-01): `line-chart`/`bar-chart` via Chart.js canvas, `stat-card` via `.stat-card-value`, `table` via plain HTML `<table>`. |
| partial | `.widget-stack` — invalid-widget drop | ✅ covered | **[auto] D-UI-02:** Widgets that fail schema validation (D-03) are silently dropped from the rendered result; no per-widget "this one was invalid" indicator is shown to the user. Only when the ENTIRE batch is empty after filtering does the full D-08 error banner appear (Pitfall 2's recommended default, now locked as a UI decision). |
| partial | `.widget-card` — per-widget fetch failure | ✅ covered | **[auto] D-UI-03:** A widget whose real `teo` fetch failed (but passed schema validation) renders as a `.widget-placeholder` with "Data unavailable for this widget" — sibling widgets in the same response render normally (Pitfall 6). |
| overflow | `.widget-card-title` | 🧪 backstop | **[auto] D-UI-05:** LLM-generated widget titles truncate with CSS ellipsis at the card-header width, with a `title` attribute carrying the full text on hover — identical mechanism to `02-UI-SPEC.md`'s `#tenant-badge-value` pattern. | zero-one-many | `.widget-stack` | ✅ covered | **[auto] D-UI-04:** 1 widget renders as a single full-width card; N widgets render as N full-width cards stacked vertically with `--space-md` gaps — never a multi-column grid, per `04-CONTEXT.md`'s `<specifics>` note ("vertical stack of the four fixed widget types"). |
| long-text | Prompt textarea | ✅ covered | No hard character limit on the prompt textarea itself (it wraps naturally); the LLM-supplied `title` field is server-capped at 120 chars (D-03/`generation-schema.js`) and truncated client-side per the overflow row above — the two long-text surfaces share one resolution mechanism. |

**Additional locked auto decisions (component/layout, not state-coverage rows):**

- **[auto] D-UI-06:** Save button click disables itself and shows "Saving…"; on success it is replaced by the "Saved ✓" confirmation state plus the retrievable link (`.save-bar`), rendered from the already-in-memory `POST /api/dashboard` response — never from an immediate `GET /api/dashboard/:id` re-fetch (sidesteps KV's 60-second eventual-consistency window per Pitfall 5).
- **[auto] D-UI-07:** The retrieval view (`/?dashboard=<id>`) renders the saved widgets **read-only** — the prompt textarea, Generate/Regenerate button, and Save button are all hidden in this view. v1 has no "edit and re-save" flow (matches D-06's "revisit the exact saved URL" scope; SHARE-01/02 remain v2).
- **[auto] D-UI-08:** Chart.js dataset color for both `line-chart` and `bar-chart` widgets uses the existing `--color-primary` (`#0052D9`) token exclusively — one dataset per widget, no multi-series palette needed, since D-02 restricts each widget to exactly one `metric`.
