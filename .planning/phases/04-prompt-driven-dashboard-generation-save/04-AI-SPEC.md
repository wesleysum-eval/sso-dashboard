## 1. System Classification

**System Type:** Extraction (constrained structured-output generation from a natural-language prompt — closest match to "Structured Data Extraction"; explicitly not Conversational, Multi-Agent, RAG, or Autonomous Agent)

**Description:**
A logged-in enterprise user, having already selected a tenant-scoped data source (CDN traffic or security events), types a natural-language prompt describing a dashboard they want. The system sends that prompt plus a fixed, closed vocabulary (4 widget component types; closed `metric`/`interval`/`timeRange` enums) to an LLM and asks for JSON only. The server strictly validates the returned JSON against the closed schema — any out-of-vocabulary value is rejected outright, never coerced — then uses only the validated enum values (never the LLM's raw strings) to fetch real tenant-scoped data via existing Phase 3 functions, and renders the result as charts/tables. The user can re-prompt to refine, and save the result. "Good" = every rendered widget is either backed by real fetched data for a validly-selected metric, or a generic placeholder — never a fabricated number, never a widget type outside the fixed four, and never a query against another tenant's data.

**Critical Failure Modes:**
1. LLM output (or any derivative of it) reaches `signTeoRequest()`/`getTenantAccount()` as a raw string instead of via the server-side enum→lookup-table mapping — this would reopen the exact injection/exfiltration risk the constrained-vocabulary design (D-01/D-02/D-03) exists to prevent.
2. A widget renders fabricated/hallucinated data values instead of the real fetched `teo` API response, or silently substitutes a "best guess" metric/interval/timeRange when the LLM's selection doesn't exactly match a closed enum value (must reject, never coerce).
3. Generation, validation, or save/retrieve failures leak raw LLM provider error bodies, API keys, or stack traces to the client instead of the generic no-leak message (D-08).
4. A saved or retrieved dashboard's tenant scoping is bypassed — e.g., `dashboard_id` alone (without session re-verification) is sufficient to read another tenant's saved dashboard (D-06's defense-in-depth guarantee).
5. The fixed 4-type component vocabulary or closed metric/interval/timeRange enums are silently expanded at runtime by prompt content (e.g., a prompt convinces the LLM to invent a 5th component type that the server then renders) — this vocabulary is a one-way, deliberate-future-decision boundary per D-01.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Developer tooling / network operations — specifically CDN & network-security observability (self-service BI/reporting over CDN traffic and DDoS/security-event telemetry, in the same practitioner space as Cloudflare Analytics, Akamai Control Center, Grafana, and Datadog dashboards).

**User Population:** Enterprise IT/DevOps/SRE staff at EdgeOne customer organizations, generating ad-hoc reports on their own account's CDN bandwidth/request/response-time metrics or DDoS attack-bandwidth/packet-rate metrics — self-service, in place of filing a support ticket. Not end-consumers; users are technically literate practitioners who already read dashboards like this daily in other tools.

**Stakes Level:** Medium. Data is real production infrastructure telemetry (not synthetic/decorative), and strict tenant isolation is Critical (see Section 1's failure mode #4/#5 and PROJECT.md's core constraint) — but the *generation* surface itself is read-only, self-service reporting, not an automated action, alert, or remediation system. A wrong/misleading chart causes a practitioner to draw an incorrect operational conclusion or waste investigation time, not to trigger an unattended action (no write/mutation paths exist per REQUIREMENTS.md's Out-of-Scope table). This is closer to "internal BI tool" stakes than "SOC/incident-response tooling" stakes.

**Output Consequence:** A generated dashboard is looked at by a human practitioner who then decides whether to escalate, investigate further, or dismiss what they see — e.g., "is this bandwidth spike a legitimate traffic surge or the start of an attack?" or "did my response time regress after last week's deploy?" The AI's output is never wired into an automated decision; the failure mode is a human being misled or under-informed, not a system acting incorrectly on its own.

### What Domain Experts Evaluate Against

```
Dimension: Metric-to-chart-type fit
Good: line-chart used for time-series metrics (l7Flow_outFlux/inFlux/bandwidth trends, attack bandwidth over time); stat-card used for single point-in-time summaries (current attack bandwidth, total requests); bar-chart used for comparative aggregates (avg vs max response time); table used for raw multi-field rows a practitioner wants to scan/export
Bad: a time-series metric (e.g., l7Flow_outFlux) rendered as a stat-card (collapses a trend into a single meaningless number) or a comparison metric rendered as a line-chart with no meaningful time axis
Stakes: High
Source: Practitioner convention across Grafana/Datadog/Cloudflare Analytics — chart-type selection is one of the first things an SRE visually checks before trusting a dashboard at all (Google SRE Workbook, Ch.4 "Interfaces": "choose formats that most clearly display the data you care about")

Dimension: Interval/timeRange coherence
Good: the selected `interval` (hour|day) is proportionate to the selected `timeRange` (e.g., last24h paired with hour, last30d paired with day) so the resulting series has a sane number of data points — not 720 hourly points crammed into a 30-day view, not 1 daily point for a 24h view
Bad: interval/timeRange combinations that produce a chart too sparse to show a trend (last24h + day = 1 point) or too dense to read (last30d + hour = 720 points) — a practitioner immediately flags this as "unreadable" or "useless," even though every point is real data
Stakes: High
Source: Google SRE Workbook Ch.4 — dashboards must be built at a granularity the audience can actually act on; standard practitioner expectation from Grafana/Datadog default interval-scaling behavior

Dimension: Traffic-vs-attack metric conflation
Good: CDN traffic metrics (l7Flow_outFlux, l7Flow_bandwidth, etc.) and security-event metrics (ddos_attackBandwidth, ddos_attackMaxBandwidth) are never presented as if interchangeable or on a shared scale/axis implying they measure the same thing; a widget's title and metric stay scoped to the single data source the user selected in Phase 3
Bad: a generated widget's title implies attack traffic when the underlying metric is ordinary CDN traffic volume (or vice versa) — e.g., titling an `l7Flow_outFlux` line-chart "Attack Traffic" — which is exactly the "legitimate spike mistaken for an attack" confusion practitioners flag as a recurring real-world false-positive/false-narrative failure in security telemetry visualization
Bad: a bandwidth spike shown without any surrounding context is inherently ambiguous (legitimate traffic surge vs. attack) — since this system has no cross-referencing/correlation capability by design (single data source per dashboard, D-02), the *title/label* must not overclaim what a single metric can tell the viewer
Stakes: Critical
Source: Security-telemetry visualization literature on DDoS detection explicitly names "attacks mimicking legitimate traffic patterns" as the central visual-ambiguity problem (arxiv.org/html/2511.04114v1); this system's own D-02 scoping (one data source per dashboard) is a structural mitigation, but title/labeling can still reintroduce the ambiguity if left unconstrained

Dimension: No fabricated or substituted values
Good: every number shown for a widget's metric is the real value returned by the `teo` API call for that exact `metric`/`interval`/`timeRange`/tenant — or the widget renders a clearly-labeled empty/error state if the fetch failed
Bad: any number in a rendered widget that did not come from a real `teo` API response for that exact validated query — including the LLM "filling in" a plausible-looking value, or the server silently substituting a nearby valid metric when the LLM's choice didn't validate
Stakes: Critical
Source: Directly maps to this AI-SPEC's own Section 1 Critical Failure Mode #2 and D-03 step 3 ("no coercion, no best-guess substitution") — restated here as the domain-expert-facing version of the same guarantee: a CDN/SRE practitioner treats a fabricated metric value as a trust-destroying event, identical to how they'd treat a monitoring system that silently interpolated fake data points (Google SRE Workbook Ch.4: "trivial operations may mask bad behavior")

Dimension: Prompt-intent-to-widget-selection fidelity
Good: the widgets generated plausibly match what a practitioner reading the prompt would expect — e.g., "show me my bandwidth usage over the last week" produces a line-chart of a bandwidth metric at day or hour interval over last7d; "how many DDoS attacks hit me today" produces a security-events widget scoped to last24h
Bad: the generated widget set ignores the prompt's explicit time scope or metric intent and defaults to an unrelated metric/timeRange combination just because it validated against the closed enum — "technically valid JSON" is not the same as "answered what was asked"
Stakes: Medium
Source: Practitioner expectation carried over from every self-service BI tool (Cloudflare Analytics, Grafana Explore) — a dashboard that is schema-valid but ignores stated intent is graded as a failure by the user even though it passes code-based validation; this is the dimension code-based checks (D-03) cannot cover and requires an LLM-judge or human rubric (see Section 5)
```

### Known Failure Modes in This Domain

1. **Attack-bandwidth/legitimate-traffic conflation.** The single most-cited real-world failure mode in DDoS/security-event visualization: a traffic spike from a legitimate cause (product launch, viral content, cache miss storm) visually indistinguishable from an attack signature unless the dashboard's labeling and metric choice are scrupulously precise about which of the two it is actually measuring. This system's per-dashboard single-data-source design (D-02) structurally limits the blast radius, but widget titles are LLM-generated free text (D-03) and are not validated for semantic accuracy — only for length/type — so this ambiguity can still surface via a misleading title on an otherwise-correct chart.
2. **Interval/timeRange mismatches producing an unreadable-but-technically-valid chart.** Because `interval` and `timeRange` are independently validated closed enums (D-02) with no cross-field validation rule enforced today, a schema-valid combination (e.g., `hour` + `last30d`) can still produce a chart no practitioner would consider usable — a "passes validation, fails the user" gap identical in shape to the classic BI pitfall of technically-correct-but-meaningless aggregation windows.
3. **Metric-to-chart-type mismatch that is schema-valid but semantically wrong.** D-01's four component types are validated independently from D-02's metric selection — nothing in the current schema (`generation-schema.js`) enforces that a time-series metric maps to `line-chart` rather than `stat-card`. A practitioner immediately distrusts a dashboard that presents a bandwidth trend as a single frozen number.
4. **Partial-success dashboards silently under-communicating what's missing.** D-03 step 4 / 4b.1's "proceed with the valid subset" design (deliberate, and correct for this system's safety goals) means a user's prompt can produce fewer widgets than the LLM proposed, with rejected widgets simply absent — a practitioner used to explicit error states in observability tooling (Grafana panel "no data" markers, Datadog widget error badges) may not notice a widget silently didn't make it into the dashboard at all, unless the UI surfaces "N of M requested widgets generated."

### Regulatory / Compliance Context

No sector-specific regulation (HIPAA/PCI/SOX/FCA-class) applies directly — this is enterprise infrastructure telemetry (CDN traffic/DDoS metrics), not personal, health, or financial data, and the system is explicitly read-only with no write/mutation actions against EdgeOne APIs (REQUIREMENTS.md Out-of-Scope). The one binding constraint that *does* function as a hard compliance-equivalent requirement in this domain is **tenant data isolation** — enterprise multi-tenant SaaS practitioners treat cross-tenant data leakage as a trust-ending incident on par with a regulatory breach even absent a named regulation, which is why this AI-SPEC's own Critical Failure Modes #4/#5 (Section 1) and D-02/D-03/D-06's "always re-derive tenant from `verifySession()`, never from LLM or client input" design already treat it at that severity. No additional regulatory research surfaced a directly relevant framework beyond this project's own existing tenant-isolation design.

## 2. Framework Decision

**Selected Framework:** No framework — raw `fetch()` against an OpenAI-compatible REST endpoint (EdgeOne Makers AI Gateway, `https://ai-gateway.edgeone.link/v1/chat/completions`, model `@makers/deepseek-v4-flash`)

**Version:** N/A (no SDK/library version to pin — plain HTTPS JSON REST call). Model string `@makers/deepseek-v4-flash` is the pinned model identifier; a one-line swap to any other OpenAI-compatible vendor model string is supported by the same gateway per D-04.

**Rationale:**
This is a single-shot, stateless, schema-constrained JSON generation call (D-01–D-03) — not RAG, not multi-agent, not a stateful graph, not autonomous tool-use. Every candidate framework's core value proposition (checkpointing, retrieval orchestration, multi-agent handoff, tool-call loops) is irrelevant to this use case. All npm-based framework candidates additionally fail the hard edge/V8-isolate runtime constraint this project already proved out in Phase 3 (`tencentcloud-sdk-nodejs` incompatibility → hand-rolled `fetch()` + `crypto.subtle` precedent). A direct REST call plus server-side closed-enum validation is strictly less code, has fewer failure modes, and is the only edge-runtime-safe option without unverified risk.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain | Broadest "requirements might evolve" framework, but adds abstraction overhead for what is currently one LLM call; not edge-runtime-verified; only worth revisiting if a second LLM-driven reasoning/retrieval step is added later |
| LlamaIndex | RAG/data-framework — no retrieval component exists or is needed in this system (widgets query `teo` APIs directly via fixed lookup table, not a vector store) |
| CrewAI / AutoGen/AG2 | Multi-agent orchestration frameworks — this system has exactly one LLM call per generation request, no agent-to-agent handoff |
| LangGraph | Stateful graph workflows — D-07 explicitly keeps refinement state client-side, not server-side graph state; no checkpointing need exists |
| OpenAI Agents SDK / Claude Agent SDK | Provider-native agent frameworks with tool-use/handoff primitives — this system needs a single constrained completion call, not agent tool orchestration; would also introduce vendor lock-in D-04 deliberately avoided |
| Any provider SDK (OpenAI Node SDK, etc.) | Unverified edge/V8-isolate compatibility, consistent with Phase 3's SDK-avoidance precedent; a plain fetch() call against an OpenAI-compatible REST shape achieves the same result with zero dependency risk |

**Vendor Lock-In Accepted:** Partial — bound to EdgeOne Makers AI Gateway's built-in model tier for v1 (explicitly documented as prototyping-scoped, not production-guaranteed, per official docs). Mitigated: the OpenAI-compatible request shape means switching to an external vendor key (OpenAI/Anthropic/Hunyuan/etc.) under the same gateway is a one-line `model` string change, not a code restructure.

## 3. Framework Quick Reference

> Fetched/verified from official docs by `gsd-ai-researcher`. Distilled for this specific use case.
> **No agent framework is used.** This system is a single-shot, stateless, schema-constrained JSON extraction call, made via plain `fetch()` from an EdgeOne Edge Function (V8-isolate runtime, not Node.js) against an OpenAI-compatible REST endpoint. Section 3 is therefore a **REST API quick reference** for the EdgeOne Makers AI Gateway, adapted from the framework-quick-reference template per `04-AI-SPEC.md` Section 2's framework decision.

### Installation
```bash
# No npm install, no SDK. Plain fetch() — zero dependency, edge-runtime-safe by construction.
# (Do NOT install the `openai` npm package — the official docs show it as an option,
# but D-04 explicitly rejects it: unverified edge/V8-isolate compatibility, same class
# of risk as Phase 3's tencentcloud-sdk-nodejs incompatibility.)
```

### Core Imports
```javascript
// None. Only runtime-native globals are used:
//   fetch()               — outbound HTTP call to the gateway
//   AbortSignal.timeout() — request timeout (NEEDS the guarded polyfill re-declared
//                            in this module — see Pitfall 1; do NOT assume
//                            edge-functions/lib/oidc-config.js already patched it)
//   crypto.subtle / crypto.randomUUID() — not used for the LLM call itself, but
//                            randomUUID() is used one hop downstream for dashboard_id
```

### Entry Point Pattern
```javascript
// edge-functions/api/generate.js — minimal working request/response shape
// for the "Extraction" system type: prompt in, validated-JSON widget spec out.

// --- Guarded polyfill (copy into THIS module; do not rely on oidc-config.js's copy) ---
if (typeof AbortSignal.timeout !== 'function') {
  AbortSignal.timeout = (ms) => {
    const controller = new AbortController();
    setTimeout(() => controller.abort(new DOMException('TimeoutError', 'TimeoutError')), ms);
    return controller.signal;
  };
}

const GATEWAY_URL = 'https://ai-gateway.edgeone.link/v1/chat/completions';

async function callGateway(systemPrompt, userPrompt, env) {
  const res = await fetch(GATEWAY_URL, {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${env.MAKERS_MODELS_KEY}`, // never sent to/readable by client
      'Content-Type': 'application/json',
    },
    // NOTE: response_format is deliberately OMITTED — see Common Pitfalls #2.
    body: JSON.stringify({
      model: '@makers/deepseek-v4-flash',
      stream: false,          // await full body for structured-output validation (4b.2)
      max_tokens: 1024,       // explicit, never unbounded in production (4b.3)
      temperature: 0.2,       // low temp for schema-compliant, low-variance extraction
      messages: [
        { role: 'system', content: systemPrompt }, // fixed vocabulary description (D-01/D-02)
        { role: 'user', content: userPrompt },     // the end user's raw prompt (untrusted input)
      ],
    }),
    signal: AbortSignal.timeout(10000), // 10s budget — see Section 4b.5
  });

  if (!res.ok) throw new Error('gateway_http_error'); // caught by caller, never leaked (D-08)
  const body = await res.json(); // OpenAI-compatible chat.completions response shape
  return body.choices?.[0]?.message?.content ?? '';
}
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| Chat Completions request | `{model, messages, stream, max_tokens, temperature}` POSTed as JSON | Every `/api/generate` call — the entire integration surface with the LLM |
| `messages` array (system/user roles) | System role carries the fixed D-01/D-02 vocabulary-as-schema; user role carries the raw human prompt + (on re-prompt) `previousSpec` context | Building the request body each call — never mix roles; never let user-controlled text into the system message |
| `response_format` (OpenAI-standard param) | `{type: 'json_object'}` — natively documented and supported by DeepSeek's own API (`api-docs.deepseek.com/guides/json_mode`), but **unconfirmed on this specific gateway passthrough** (absent from all EdgeOne Makers docs pages checked) | Deliberately **omitted** in this system per D-04's locked recommendation — see Common Pitfalls #2 |
| `stream: false` | Non-streaming mode — waits for the full response body before returning | Always, for this system type — a structured-output extraction call must validate the complete JSON before use; streaming is for UX-facing chat, not this pipeline (4b.2) |
| `finish_reason` | `"stop"` \| `"length"` \| other | Check for `"length"` specifically — indicates `max_tokens` truncated the JSON mid-object, which will fail `JSON.parse()` and should route to the retry-once path (D-03 step 4), not a generic parse-error path |

### Common Pitfalls
1. **Assuming `AbortSignal.timeout` is already polyfilled because `oidc-config.js` patched it once.** The polyfill is a guarded module-level side effect — it only fires when that specific module is imported in the current warm instance. `generate.js` has no reason to import `oidc-config.js`, so a cold instance hitting `/api/generate` directly will throw `TypeError: AbortSignal.timeout is not a function`. **Fix:** copy the same guarded snippet directly into `generate.js` (shown above), or extract to a shared `lib/polyfills.js` both modules import.
2. **Passing `response_format: {type: 'json_object'}` when the gateway's support is unconfirmed.** DeepSeek's native API supports and requires it for JSON mode, but the EdgeOne Makers gateway's own docs (models / models-vendor-keys-openai / models-faqs pages) never mention `response_format` at all — passing an unrecognized field to an OpenAI-compatible passthrough could be silently ignored (harmless) or rejected by strict validation (a hard 4xx failure with no fallback). **Fix:** omit the parameter entirely; rely on prompt-engineered "return ONLY valid JSON" instructions plus D-03's mandatory server-side schema validation, which is the safety backstop regardless of native JSON-mode support.
3. **Trusting `finish_reason: "stop"` alone as proof of valid JSON.** A model can stop cleanly while still having produced prose, markdown code fences (```json ... ```), or a JSON object that doesn't match the fixed vocabulary. **Fix:** always strip markdown fences before `JSON.parse()`, and always run the parsed object through the closed-enum validator (`generation-schema.js`) — `finish_reason` only tells you generation completed, not that the content is schema-valid.
4. **Letting the retry-once correction prompt (D-03 step 4) balloon `max_tokens` or context on the second call.** A common mistake is re-sending the entire failed response plus a lengthy correction as new context, silently growing the token budget/cost per generation. **Fix:** the retry call should be a fresh, minimal request — same system prompt, user prompt + a short explicit instruction ("Your previous response was not valid JSON. Return ONLY a JSON array matching the schema, no markdown, no explanation."), not an accumulating conversation.
5. **Treating the built-in model tier as production-guaranteed capacity.** `@makers/deepseek-v4-flash` is explicitly documented as prototyping/technical-validation scope, subject to automatic rate-limiting on non-organic usage patterns. **Fix:** design the failure path (D-08) to treat a 429/rate-limit response identically to any other gateway failure — generic no-leak message, no special-casing that assumes it "shouldn't happen."

## 4. Implementation Guidance

**Model Configuration:**
- Model: `@makers/deepseek-v4-flash` (EdgeOne Makers built-in tier, per D-04 — one-line swappable to any OpenAI-compatible vendor model string under the same gateway if production-grade reliability is needed later)
- `temperature: 0.2` — low, favors deterministic, schema-compliant output over creative variance; this is closed-vocabulary extraction, not open-ended content generation
- `max_tokens: 1024` — explicit and bounded (4b.3); a widget array of the fixed 4 component types with short `title` strings comfortably fits well under this ceiling, and it prevents an unbounded/runaway completion from a malformed prompt
- `stream: false` — always; the response must be fully buffered and validated before any widget's data-fetch step runs (4b.2)
- `response_format` — **deliberately omitted** (Common Pitfalls #2)

**Core Pattern:**
The entry-point pattern in Section 3 is the complete core pattern for this system type: build a system prompt describing the fixed D-01/D-02 vocabulary as a schema (not example code), send it alongside the user's prompt (and `previousSpec` on re-prompt, D-07), await the full response, then hand the raw string to the 4b.1 validation pipeline before any `teo` data is fetched. There is no chaining, no tool-call loop, no multi-turn agent state — one request in, one validated widget array out, exactly matching the "Extraction" system type's minimal-complexity shape.

**Tool Use:**
None. This system does not use LLM tool-calling/function-calling at all — the LLM's only job is to emit JSON matching a schema described in the prompt. The "real tool use" (fetching `teo` API data) happens entirely server-side, *after* validation, driven by the server's own fixed lookup table (`metric-lookup.js`), never by an LLM-issued tool call. This is a deliberate simplification consistent with D-03's "server is the only thing that constructs real API params" guarantee — introducing native tool-calling would only add a second, unnecessary trust boundary to defend.

**State Management:**
Fully stateless per request, matching D-07. No conversation object, no server-side session/thread ID is created or persisted for the LLM call itself. Re-prompt (GEN-04) is implemented by the *client* re-sending `previousSpec` as plain JSON context in the user message on the next `/api/generate` call — the server has no memory between calls. The only state this phase persists anywhere is the final, explicit Save action (D-05) writing to KV, which is entirely downstream of and decoupled from the LLM call itself.

**Context Window Strategy:**
Not a meaningful concern for this system type at this scale — a single system prompt (fixed vocabulary description, roughly constant size) plus one user prompt (short natural-language request, optionally plus a compact `previousSpec` JSON blob on re-prompt) is orders of magnitude below any modern model's context window. No chunking, retrieval, reranking, or summarization is needed. The one discipline to maintain as this evolves: keep `previousSpec` passed on re-prompt to the *validated, compact* widget array (Pattern 1's output shape: `{componentType, metric, interval, timeRange, title}` per widget) — never the full fetched data snapshot — so re-prompt context stays small and bounded regardless of how much data a widget's chart contains.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.
> This project has no Python/Pydantic anywhere (JavaScript/V8-isolate edge runtime) — 4b.1 below is adapted to the equivalent hand-rolled JSON-Schema-style validation pattern this project's own D-01/D-02/D-03 design already specifies, not real Pydantic code.

### 4b.1 Structured Outputs — Hand-Rolled Schema Validation (JS equivalent of Pydantic)

There is no Pydantic (Python-only) or `instructor` in this stack. The equivalent contract — "the LLM must emit data matching a defined shape, and the system must validate or retry" — is implemented as a plain JS validation function plus a closed-enum lookup, defined once in `edge-functions/lib/generation-schema.js` and used both to describe the schema to the LLM *and* to validate its response (single source of truth, per `04-RESEARCH.md`'s Recommended Project Structure):

```javascript
// edge-functions/lib/generation-schema.js
// The "schema model" for this system — the direct equivalent of a Pydantic
// BaseModel + Field(enum=...) definition, expressed as plain JS constants
// and a validator function instead of a class.

export const COMPONENT_TYPES = ['line-chart', 'bar-chart', 'stat-card', 'table']; // D-01
export const INTERVALS = ['hour', 'day'];                                          // D-02
export const TIME_RANGES = ['last24h', 'last7d', 'last30d'];                       // D-02
export const METRICS_BY_SOURCE = {
  'cdn-traffic': ['l7Flow_outFlux', 'l7Flow_inFlux', /* ...full 10-value enum */],
  'security-events': ['ddos_attackMaxBandwidth', /* ...full 4-value enum */],
};

/**
 * Validates ONE candidate widget object against the closed vocabulary.
 * Returns a clean, typed widget object on success, or null on ANY violation —
 * never coerces, never substitutes a "best guess" (D-03 step 3's core rule).
 * This is the functional equivalent of Pydantic's `model_validate()` raising
 * ValidationError — except here it returns null instead of throwing, because
 * this system's contract is "reject the widget," not "reject the request."
 */
export function validateWidget(widget, dataSource) {
  if (!widget || typeof widget !== 'object') return null;
  const { componentType, metric, interval, timeRange, title } = widget;
  if (!COMPONENT_TYPES.includes(componentType)) return null;
  if (!METRICS_BY_SOURCE[dataSource]?.includes(metric)) return null;
  if (!INTERVALS.includes(interval)) return null;
  if (!TIME_RANGES.includes(timeRange)) return null;
  return { componentType, metric, interval, timeRange, title: String(title || '').slice(0, 120) };
}

/** Parses the raw LLM string into an array of validated widgets (partial success). */
export function parseAndValidate(rawContent, dataSource) {
  let candidates;
  try {
    const stripped = rawContent.trim().replace(/^```(json)?/i, '').replace(/```$/, '');
    const parsed = JSON.parse(stripped);
    candidates = Array.isArray(parsed) ? parsed : parsed?.widgets;
  } catch {
    return { widgets: [], parseFailed: true }; // triggers D-03 step 4's retry path
  }
  if (!Array.isArray(candidates)) return { widgets: [], parseFailed: true };
  const widgets = candidates.map(w => validateWidget(w, dataSource)).filter(Boolean);
  return { widgets, parseFailed: false };
}
```

**How this integrates into the request/response cycle:** there is no framework-provided `.with_structured_output()` or `response_format` to lean on (Section 3, Pitfall 2) — the *entire* structured-output guarantee comes from this hand-rolled validator, called immediately on every gateway response, before any widget's data is fetched.

**Retry logic:**
1. Call the gateway once. Run `parseAndValidate()`.
2. If `parseFailed === true` OR `widgets.length === 0`: retry **exactly once** with a corrected, minimal prompt ("Your previous response was not valid JSON matching the schema. Return ONLY a JSON array, no markdown, no explanation.") — log the raw failed content server-side only (never to the client, D-08), tagged with a reason code (`parse_error` vs `zero_valid_widgets`) for later flywheel analysis (Section 7).
3. If the second attempt also fails: surface the generic D-08 no-leak message ("Couldn't generate a dashboard from that prompt — try rephrasing"). Never surface the raw LLM content, the raw parse error, or the gateway's HTTP error body.
4. If `widgets.length > 0` (even if fewer than the LLM originally proposed): proceed with the valid subset — partial success, not all-or-nothing (Pitfall 2 in `04-RESEARCH.md`). This is a deliberate divergence from a typical Pydantic "raise on any invalid field" pattern, chosen because a "prototyping-tier" model (D-04's own caveat) will realistically produce a mix of valid/invalid widgets often enough that all-or-nothing would degrade UX for no security benefit — per-widget rejection already achieves D-03's safety guarantee.

### 4b.2 Async-First Design

Edge Functions export `async function onRequestPost(context)` handlers — every I/O call (`fetch()` to the gateway, `fetch()` to `teo`, `my_kv.get`/`put`) is a native `Promise`, `await`ed directly; there is no separate sync/async API split to worry about (unlike, e.g., Python's `asyncio.run()` vs. an already-running event loop — that specific footgun does not exist in this runtime).

**The one common mistake in this codebase's context:** firing the multiple per-widget `teo` fetches in this phase's request sequentially (`for (const w of widgets) { await fetchTeoData(w) }`) instead of concurrently. A dashboard with 3-4 widgets doing sequential round-trips to `teo.tencentcloudapi.com` needlessly multiplies end-to-end latency. **Fix:** `await Promise.all(widgets.map(w => fetchTeoData(w)))` — since each widget's fetch is already independently no-leak/fail-soft (Pitfall 6 in `04-RESEARCH.md`: one widget's `teo` failure shouldn't sink the others), `Promise.allSettled()` is actually the more correct choice so one rejected promise doesn't reject the whole batch.

**Stream vs. await:** the official gateway curl example defaults to `"stream": true` (for chat-UI token-by-token display), but this system explicitly sets `stream: false` (Section 3/4). Streaming is for user-facing conversational UX where partial tokens can be rendered as they arrive; this system needs the **complete** response before it can be JSON-parsed and schema-validated (4b.1) — validating a partial/truncated JSON string is meaningless. Always `await` the full body here; never stream a structured-extraction call.

### 4b.3 Prompt Engineering Discipline

**System vs. user separation:** the `system` message carries only the fixed, server-owned vocabulary description (D-01/D-02's enum lists, rendered as a schema description, not example code) — content the LLM must treat as its operating constraints. The `user` message carries only the human's raw prompt text (and, on re-prompt, the previous validated spec as JSON context). **Never concatenate user input into the system message** — that would blur the trust boundary this project treats as load-bearing everywhere else (session/tenant scoping) and open the door to a prompt convincing the model that user-supplied text is itself a system-level instruction.

**Few-shot:** inline, not dynamically retrieved — a single illustrative example widget object embedded directly in the system prompt (e.g., `{"componentType":"line-chart","metric":"l7Flow_outFlux","interval":"hour","timeRange":"last24h","title":"Traffic last 24h"}`) is sufficient for a closed 4-type/4-enum vocabulary this small; there is no corpus of examples large enough to warrant a retrieval step, and adding one would be unjustified complexity for this system's scope.

**`max_tokens`:** set explicitly to `1024` (Section 4) in every call, including the retry — never left unbounded. An unbounded `max_tokens` on a "prototyping-tier" model (D-04) risks both a slow/costly runaway completion and a higher chance of the model wandering into explanatory prose around the JSON, which then has to be stripped before parsing.

### 4b.4 Context Window Management

This system type ("Extraction") has the simplest possible context-management story of the categories the parent skill covers — no RAG chunking/reranking (no retrieval component exists per Section 2's rationale), no multi-turn conversation summarization (D-07 keeps refinement state client-side, not accumulated server-side), no autonomous-agent compaction (no agentic loop exists). The only discipline that matters as this evolves:

- **Bound what `previousSpec` carries on re-prompt** to the compact validated widget array (5 fields × N widgets), never the full fetched data snapshot — this keeps every re-prompt call's context size roughly constant regardless of how much underlying `teo` data a widget represents (Section 4's Context Window Strategy).
- **Do not let the retry-once correction prompt (4b.1) accumulate** the previous failed response as growing context — each retry is a fresh, minimal request (Section 3, Pitfall 4).

### 4b.5 Cost and Latency Budget

**Cost:** `$0` per call — `@makers/deepseek-v4-flash` is EdgeOne Makers' free built-in tier (D-04, confirmed via official FAQ: "The Makers Models feature is completely free"). The only cost consideration is the *rate-limiting* risk on non-organic usage patterns the same docs flag, not a per-token bill. If this system later swaps to an external vendor key (D-04's documented one-line `model` string change), the cost model becomes real and this section must be revisited with an actual per-token estimate for the chosen vendor/model at expected prompt volume.

**Latency budget:** target end-to-end `/api/generate` response time under ~5-8s for a typical single-generation request (1 gateway round-trip ~1-4s for a small/fast model + N concurrent `teo` fetches, each independently timed against Phase 3's existing `AbortSignal.timeout` budget). The gateway call itself uses a 10s abort budget (Section 3's entry point pattern) — generous enough to tolerate the built-in tier's variable prototyping-scope latency without hanging a request indefinitely, tight enough to fail fast into the D-08 generic-error path rather than leaving the user staring at a spinner.

**Caching:** not applicable in a strong sense for v1 — each prompt is a distinct, personalized natural-language request, so exact-match caching would rarely hit. **What is worth doing:** cache nothing about the LLM call itself, but do treat a **re-prompt with an unchanged `previousSpec` and near-identical new prompt** as a candidate for future semantic-similarity caching if generation volume ever becomes a real cost/latency concern — explicitly deferred, not needed at this phase's scope (single free-tier model, no per-token cost pressure).

**Cheaper models for sub-tasks:** not applicable — this system has exactly one LLM call per generation request (Section 4's Tool Use), with no separate classification/routing/summarization sub-task to offload to a smaller model. If a future phase adds, e.g., a separate "classify this prompt's intent before generating" step, that would be the first candidate for a cheaper/faster model tier under the same gateway.

## 5. Evaluation Strategy

> This system is "Extraction" (constrained structured-output generation), so code-based schema validation is the primary and cheapest measurement layer — D-01/D-02/D-03's `validateWidget()`/`parseAndValidate()` (Section 4b.1) is not just implementation, it is the first eval. LLM judges are reserved for the dimensions Section 1b explicitly flags as un-checkable by schema validation alone (chart-type fit, title/metric conflation, prompt-intent fidelity). No Python exists in this stack (pure JS/V8-isolate edge runtime) — tooling choices below are deliberately npm/CLI-native, not Python-library-based.

### Dimensions

| Dimension | Rubric (Pass/Fail) | Measurement Approach | Priority |
|-----------|--------------------------|---------------------|----------|
| **Schema/enum compliance** (GEN-03, D-01/D-02/D-03) | PASS: every widget in the generated array has `componentType` ∈ the 4 fixed types, `metric` ∈ the selected data source's closed allow-list, `interval` ∈ {hour,day}, `timeRange` ∈ {last24h,last7d,last30d}. FAIL: any widget reaches the client, or reaches `metric-lookup.js`, with a value outside its closed enum — including "close but not exact" strings the LLM might emit (coercion is itself a FAIL, not just an out-of-vocab value). | Code — `validateWidget()` unit-tested directly + assertion on every eval-dataset run | Critical |
| **No fabricated/substituted data values** (Section 1b) | PASS: every number rendered in a widget is the literal value returned by the real `teo` API call for that widget's exact validated `metric`/`interval`/`timeRange`/tenant, or the widget shows a labeled empty/error state. FAIL: any rendered number that did not come from that exact `teo` response — LLM-filled placeholder values, or server substituting a nearby valid metric when the LLM's choice failed validation. | Code (diff rendered widget values against raw `teo` response in test harness) + Human spot-check on sampled real generations | Critical |
| **Tenant isolation on generation/save/retrieve** (D-02/D-03/D-06, Critical Failure Mode #4) | PASS: every `teo` fetch and every KV read/write during generation, save, and retrieval uses `tenant_id` derived exclusively from `verifySession()`; a crafted `dashboard_id` alone never retrieves another tenant's dashboard. FAIL: any code path where a client-supplied or LLM-derived string reaches `getTenantAccount()`/`signTeoRequest()`/the KV key directly. | Code — adversarial test cases (cross-tenant `dashboard_id` guess) in reference dataset + static check that `metric-lookup.js`/`generate.js`/`dashboard/[id].js` never read `tenant_id` from `context.request` or the LLM response | Critical |
| **No-leak error handling** (D-08, Critical Failure Mode #3) | PASS: every failure branch (gateway error, timeout, validation failure ×2, KV read/write failure) returns one of the pre-defined generic messages only. FAIL: any response body, header, or log reaching the client containing a raw provider error string, `MAKERS_MODELS_KEY`, a stack trace, or raw LLM content. | Code — regex assertion over every error-path response body in the eval harness (see Guardrail #3, Section 6) | Critical |
| **Metric-to-chart-type fit** (Section 1b) | PASS: time-series metrics (`l7Flow_outFlux`/`inFlux`/`bandwidth`, `ddos_attack*` over time) → `line-chart`; single point-in-time summaries → `stat-card`; comparative aggregates (avg vs max) → `bar-chart`; raw multi-field rows → `table`. FAIL: a time-series metric rendered as `stat-card` (collapses a trend into one number) or a comparison rendered as `line-chart` with no meaningful time axis. | LLM Judge (rubric calibrated by senior SRE/DevOps practitioner, Section 1b's Domain Expert Roles) | High |
| **Interval/timeRange coherence** (Section 1b, Known Failure Mode #2) | PASS: `interval`/`timeRange` pairing yields a readable point count — roughly ≤48 points for `hour` and a sane multi-point series for `day` (e.g. `hour`+`last24h`, `day`+`last7d`, `day`+`last30d`). FAIL: combinations producing an unreadable-but-schema-valid chart, e.g. `hour`+`last30d` (~720 points) or `day`+`last24h` (1 point). | Code — pure function `isCoherentPairing(interval, timeRange)`, deterministic, no LLM needed | High |
| **Traffic-vs-attack title/metric conflation** (Section 1b, Known Failure Mode #1, Critical Failure Mode risk) | PASS: a widget's LLM-generated `title` never implies the opposite data source from its actual `metric` (e.g. no "Attack Traffic" title on an `l7Flow_outFlux` widget; no "Bandwidth Usage" title on a `ddos_attackBandwidth` widget) — title stays scoped to the single data source selected in Phase 3. FAIL: any title creating a security/traffic mismatch with its underlying metric. | LLM Judge (rubric calibrated by senior SRE/DevOps practitioner; this is explicitly the dimension Section 1b flags as un-catchable by D-03's schema validation, which checks `title` only for length/type) | Critical |
| **Prompt-intent-to-widget-selection fidelity** (Section 1b) | PASS: the generated widget set plausibly answers what the prompt asked — e.g. "bandwidth usage over the last week" → a bandwidth-family metric at `last7d`. FAIL: schema-valid widgets that ignore the prompt's stated time scope or metric intent ("technically valid JSON" but didn't answer the question). | LLM Judge (rubric calibrated by senior SRE/DevOps practitioner) | Medium |
| **Partial-success transparency** (Section 1b, Known Failure Mode #4) | PASS: when fewer widgets are returned than the LLM proposed (per-widget rejection, 4b.1 step 4), the response includes enough information for the UI to say "N of M requested widgets generated." FAIL: rejected widgets silently vanish with no count signal anywhere in the response payload. | Code — assert response shape includes `requestedCount`/`generatedCount` (or equivalent) whenever `widgets.length < candidates.length` | Medium |

### Eval Tooling

**Primary Tool:** **Promptfoo** (npm, CLI-first, zero platform account) — chosen over the Arize Phoenix default because this stack has no Python anywhere (pure JS/V8-isolate edge runtime, Section 4b's own framing), this is a solo/auto-mode project with no confirmed eval budget, and `ai-evals.md`'s own tool-selection table recommends "Structured extraction → Promptfoo + code-based validators," which is exactly this system's shape. Promptfoo supports both `javascript` assertions (calling `validateWidget()`/`isCoherentPairing()` directly — the Code-measured rows above) and `llm-rubric` assertions (the LLM Judge rows above) in one config, with results as a local HTML report — no hosted infra required.

**Setup:**
```bash

# Config lives at evals/promptfooconfig.yaml (new dir, sibling to edge-functions/)

# so the eval exercises the real gateway contract, not a mock.
```

```yaml

  - id: file://evals/provider.js   # wraps callGateway() + parseAndValidate()

  - file://evals/system-prompt.txt  # the same D-01/D-02 vocabulary description generate.js sends

```

### Reference Dataset

**Size:** 15 examples to start (above the 10-example floor, below the 20-example production target — appropriate for this phase's scope: 2 data sources × a handful of prompt patterns each).

**Composition:**
- 4× clear-intent CDN traffic prompts (e.g. "show me my bandwidth usage over the last week") — critical path, GEN-01/GEN-02
- 3× clear-intent security-events prompts (e.g. "how many DDoS attacks hit me today") — critical path, tests traffic-vs-attack conflation dimension directly
- 2× colloquial/ambiguous time-range phrasing (e.g. "recently", "this month") — tests interval/timeRange coherence and prompt-intent fidelity
- 2× adversarial prompts attempting to induce an out-of-vocabulary component type or raw metric string (e.g. "render this as a pie chart" or "query metric xyz123 directly") — tests schema/enum compliance under pressure, Critical Failure Mode #5
- 2× re-prompt/refinement chains (initial prompt + follow-up `previousSpec` context) — tests GEN-04's stateless-per-request contract (D-07)
- 1× cross-tenant probing attempt (a `dashboard_id` guess against a different tenant's saved dashboard) — tests tenant isolation dimension, Critical Failure Mode #4
- 1× intentionally malformed/nonsensical prompt expected to produce zero valid widgets — tests the retry-once path (4b.1 step 2) and no-leak fallback (D-08)

**Labeling:** Per Section 1b's Domain Expert Roles table — the senior DevOps/SRE practitioner role labels each example's expected widget spec (golden `componentType`/`metric`/`interval`/`timeRange`) and calibrates the LLM-judge rubric wording for the three LLM-judge dimensions (metric-to-chart-type fit, traffic-vs-attack conflation, prompt-intent fidelity) against their own pass/fail judgment before that rubric is trusted in CI. The product owner role reviews and approves final rubric wording (per Section 1b). Dataset creation starts now, alongside/before planning — not after implementation.

## 6. Guardrails

> These guardrails run **on top of** the existing D-01/D-02/D-03 closed-enum validation and D-08 no-leak convention — they are additional checks the validation doesn't already cover (coherence/semantic checks, tenant-key assertion, response-body leak scanning), not a re-implementation of `validateWidget()` itself. `validateWidget()`/`parseAndValidate()` already ARE the primary online guardrail against Critical Failure Modes #1, #2, and #5 (Section 1) — listed here as row 1 for completeness, not as new work.

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Closed-enum schema validation (existing, D-01/D-02/D-03, `validateWidget()`) | Every widget in every LLM response, before any `teo` fetch | Block — reject the individual widget (partial-success model, 4b.1 step 4); reject the whole request only if zero widgets validate after one retry |
| Tenant-key assertion on save/retrieve | Every KV write (`dashboard:<tenant_id>:<dashboard_id>`) and read (`GET /api/dashboard/:id`) | Block — hard-fail if the code path about to construct a KV key derives `tenant_id` from anything other than the current request's `verifySession()` result (assert-and-throw in `dashboard/[id].js`, not just a convention to remember) |
| Interval/timeRange coherence check | Every validated widget, after schema validation, before rendering | Flag — do not block generation (a coherent-but-sparse chart is not catastrophic), but tag the widget with a `low_confidence` marker the UI can surface (e.g. a small "this view may be hard to read" note), consistent with keeping guardrails minimal per this step's guidance |
| No-leak response scanning | Every error-path response body, right before it's sent to the client (D-08 paths: generation failure, save failure, retrieve failure) | Block — regex/string-match assertion that the outgoing body never contains `MAKERS_MODELS_KEY`, `SESSION_SIGNING_KEY`, a raw stack trace pattern, or the raw LLM `content` string; if a match is found, replace with the generic message and log the near-miss server-side only |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Retry-path frequency (`parse_error` vs `zero_valid_widgets` reason codes, 4b.1 step 2) | 100% of generation requests (cheap counter, no sampling needed) | If retry rate climbs above a rough baseline (e.g. >15% of requests needing a retry), investigate whether the system prompt's schema description needs tightening, or whether `@makers/deepseek-v4-flash`'s prototyping-tier reliability (D-04's own caveat) has degraded |
| Metric-to-chart-type fit / traffic-vs-attack conflation / prompt-intent fidelity (the 3 LLM-judge dimensions) | Weighted sample toward re-prompted generations (a re-prompt is itself a signal the first attempt didn't satisfy the user) + a flat 10% random sample of all other generations | Below-threshold judge scores route to the senior SRE practitioner for human review; recurring failure patterns feed back into the system prompt's few-shot example (4b.3) or the fixed vocabulary itself (Claude's Discretion items) |
| Partial-success rate (widgets requested vs widgets generated) | 100% of generation requests (cheap counter from `parseAndValidate()`'s return shape) | If a meaningful share of requests are losing widgets silently, prioritize the Section 1b Known Failure Mode #4 UI fix ("N of M requested widgets generated" surfacing) sooner rather than later |

## 7. Production Monitoring

**Tracing Tool:** **Structured JSON console logging** (zero dependency, no SDK) rather than Phoenix/Langfuse/LangSmith. Rationale: this project has an established, repeated precedent (Phase 3's SDK-avoidance, D-04's own framing) of never adding an unverified npm dependency to the Edge Function/V8-isolate runtime — every tracing SDK candidate (Langfuse JS SDK, OTel JS SDK, Phoenix's OTel instrumentation) is unconfirmed on this specific edge runtime, the same class of risk `tencentcloud-sdk-nodejs` already failed here once. `console.log(JSON.stringify({...}))` from within `generate.js`/`dashboard/[id].js` is edge-safe by construction (no import, no network call, no cold-start risk) and EdgeOne Edge Functions' own platform log viewer captures it — sufficient for this solo/auto-mode project's confirmed scale. **Upgrade path (explicitly deferred, not built this phase):** if generation volume or team size grows enough to need queryable trace search/dashboards, self-hosted Langfuse (JS SDK) is the next candidate to evaluate — but only after confirming its SDK is edge/V8-isolate-safe, following the same verification discipline as every other dependency decision in this project.

**Log event shape (emit at each of these points in `generate.js`/`dashboard/[id].js`):**
```javascript
console.log(JSON.stringify({
  event: 'generation_attempt',       // | 'generation_retry' | 'generation_result' | 'save' | 'retrieve'
  tenantId: payload.tenant_id,       // from verifySession(), never client input
  dataSource,                        // 'cdn-traffic' | 'security-events'
  requestedWidgetCount: candidates?.length ?? null,
  validatedWidgetCount: widgets.length,
  parseFailed,                       // boolean, from parseAndValidate()
  reasonCode,                        // 'parse_error' | 'zero_valid_widgets' | null
  gatewayLatencyMs,
  timestamp: new Date().toISOString(),
  // NEVER logged: raw prompt text, raw LLM content, MAKERS_MODELS_KEY, dashboard data values
}));
```

**Key Metrics to Track:**
1. **Retry rate** — `generation_retry` events / total `generation_attempt` events (offline flywheel row 1, Section 6)
2. **Zero-valid-widget rate** — requests where `validatedWidgetCount === 0` after retry (feeds the D-08 fallback-message path; a rising rate signals prompt-engineering or model-quality drift)
3. **Partial-success rate** — `validatedWidgetCount < requestedWidgetCount` (offline flywheel row 3, Section 6)
4. **Gateway latency** (p50/p95 of `gatewayLatencyMs`) — against the ~5-8s end-to-end budget already set in Section 4b.5
5. **Cross-tenant retrieval attempts** — count of `dashboard/[id].js` requests where the resolved KV key (`dashboard:<verified_tenant_id>:<id>`) returns nothing because the ID belongs to a different tenant's key — a nonzero-but-low rate is expected (typos/stale links); a spike is a probing signal

**Alert Thresholds:**
- Zero-valid-widget rate > 20% over any rolling 50-request window → investigate system prompt / model tier degradation (D-04's own "prototyping-tier, not production-guaranteed" caveat means this is a real, expected risk, not hypothetical)
- Gateway p95 latency > 8s → investigate gateway-side rate-limiting (Section 3, Pitfall 5) before assuming a code regression
- Any `console.log` line matching a leaked-secret pattern (should be impossible per the no-leak guardrail, Section 6) → treat as a Critical-severity bug, not a monitoring metric — this should never fire

**Smart Sampling Strategy:**
Weight human/LLM-judge review sampling toward: (1) every re-prompt/refinement chain (a second prompt for the same session is itself a "the first attempt didn't satisfy the user" signal, per `ai-evals.md`'s smart-sampling guidance), (2) every request that hit the retry path, (3) a flat 10% random sample of otherwise-clean single-shot generations to catch silent quality drift the above two filters wouldn't surface. This mirrors Section 6's offline flywheel sampling for the three LLM-judge dimensions.
